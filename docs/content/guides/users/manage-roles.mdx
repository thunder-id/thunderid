# Roles

A role in <ProductName /> is a named set of permissions that you assign to users, groups, applications, or agents. Roles connect the permissions defined in your [resource servers](../../resource-servers) to the principals that need access to them.

Each role:

- Belongs to an **Organization Unit (OU)**, which defines the organizational scope of the role.
- Contains a set of **permissions** drawn from one or more resource servers.
- Has zero or more **assignments**: the users, groups, applications, or agents that hold the role.

## Prerequisites

Before creating a role, you need:

- An organization unit to scope the role. See [Organization Units](../../organization-units/manage-organization-units).
- At least one resource server with defined permissions. See [Resource Servers](../../resource-servers).

## Permission Requirements

<ProductName /> prevents you from granting permissions you do not hold yourself. This applies whether the recipient is another principal or your own account.

You can perform the following operations only if you already hold every permission involved:

| Operation | Requirement |
|-----------|-------------|
| Create a role with permissions | You hold every permission in the new role. |
| Update a role's permissions | You hold every permission in the updated set. |
| Add or remove a role assignment | You hold every permission the role grants. |

Permissions are compared per resource server. A permission you hold on one resource server does not satisfy a requirement on a different resource server, even when the two permission strings are identical.

The comparison respects the permission hierarchy. If you hold `system:user`, you can grant `system:user:view`, because the parent permission covers its children. The reverse does not apply: holding `system:user:view` does not let you grant `system:user`.

Holders of the root `system` permission are exempt, since that permission already authorizes every system operation.

If an operation would grant more than you hold, the API returns `403 Forbidden` with the error code `SAZ-4030`, and no change is made.

:::note
Because you must hold a permission to grant it, an administrator whose job is to manage role assignments needs to hold the permissions they distribute. Grant such an administrator the union of the permissions they are expected to assign.
:::

## System Permissions

The **System** resource server declares the permissions for managing <ProductName /> itself. Each permission has the form `system:<resource>:<action>`. The root permission `system` covers every system operation, and a resource permission such as `system:user` covers every action on that resource.

| Resource | Display name | Actions |
|----------|--------------|---------|
| `ou` | Organization Units | `view`, `create`, `update`, `delete` |
| `user` | Users | `view`, `create`, `update`, `delete` |
| `group` | Groups | `view`, `create`, `update`, `delete` |
| `agent` | Agents | `view`, `create`, `update`, `delete` |
| `usertype` | User Types | `view`, `create`, `update`, `delete` |
| `agenttype` | Agent Types | `view`, `create`, `update`, `delete` |
| `notificationtemplate` | Notification Templates | `view`, `create`, `update`, `delete` |
| `app` | Applications | `view`, `create`, `update`, `delete` |
| `role` | Roles | `view`, `create`, `update`, `delete` |
| `rs` | Resource Servers | `view`, `create`, `update`, `delete` |
| `connection` | Connections | `view`, `create`, `update`, `delete` |
| `flow` | Flows | `view`, `create`, `update`, `delete` |
| `vc` | Verifiable Credentials | `view`, `create`, `update`, `delete` |
| `project` | Projects | `view`, `create`, `update`, `delete` |
| `design` | Design | `view`, `create`, `update`, `delete` |
| `i18n` | Translations | `view`, `create`, `update`, `delete` |
| `gateway` | Gateways | `view`, `create`, `update`, `delete` |
| `authzdetail` | Authorization Detail Types | `view`, `create`, `update`, `delete` |
| `serverconfig` | Server Configuration | `view`, `update` |
| `configversion` | Configuration Versions | `view`, `create` |

The `app`, `user`, `role`, `connection`, and `flow` resources each hold a `sharing` resource with the `view`, `create`, `update`, and `delete` actions, for example `system:app:sharing:view`. The parent permission covers it, so `system:app` covers `system:app:sharing:view`. The sharing policy APIs of these resources require the `sharing` permissions: `view` to read and list policies, `create` to create one, `update` to update one, and `delete` to delete one. `system:<resource>:update` doesn't cover sharing policies.

Design, translations, gateways, authorization detail types, server configuration, and configuration versions have no owning organization unit, so a change to one affects every organization unit. A configuration version holds a snapshot of the whole deployment, so once a management API accepts `system:configversion:view`, it will expose the configuration of every organization unit. No management API accepts that permission yet.

The management APIs and MCP tools accept these permissions for every resource.

| Permission | Grants |
|------------|--------|
| `system:<resource>:view` | Read and list the resource. |
| `system:<resource>:create` | Create the resource. |
| `system:<resource>:update` | Update the resource and the parts that belong to it. |
| `system:<resource>:delete` | Delete the resource. |
| `system:<resource>` | Every action on the resource. |

Changing a part of a resource updates that resource. For example, `system:role:update` covers adding and removing role assignments, `system:rs:update` covers creating and deleting the resources and actions of a resource server, and `system:flow:update` covers restoring a flow version.

The following exceptions apply:

- Reading translations is public. `system:i18n:update` sets translation overrides and `system:i18n:delete` clears them.
- `system:vc:view` also reads the trust anchors that presentations are verified against.
- The variables and secrets of a gateway require the root `system` permission, as the server's own variable store does.
- The variable store, import, and export require the root `system` permission.

Only `ou`, `user`, `group`, `agent`, `usertype`, and `agenttype` permissions are confined to an organization unit. The other permissions aren't confined to an organization unit yet. A caller with a `system:role`, `system:flow`, or `system:app` permission, for example, can act on the roles, flows, or applications of every organization unit.

:::warning
The `flow`, `role`, `rs`, `authzdetail`, and `app` permissions are high impact, and they reach every organization unit. A flow administrator controls how users sign in and register. A role administrator decides who holds which permissions, within the permissions they hold themselves. A resource server administrator defines the permissions that roles grant to applications and APIs. An authorization detail type administrator defines what users consent to. An application administrator controls which scopes an application can request and which flows its users sign in and register through. Grant them only to administrators you trust with the whole deployment.
:::

`system:serverconfig:update` changes deployment-wide security settings such as CORS, the content security policy, and sessions.

The MCP tools require the same permissions as the matching APIs. The MCP server itself requires a token that carries at least one system permission.

If you set `server.security.system_permission_prefix`, the management APIs expect every system permission to start with that prefix, for example `mgmt:system:user:view`. The permissions declared on the System resource server don't include the prefix. To grant the prefixed permissions, declare them on a resource server of your own, for example with a root resource `mgmt` that holds `system` and its resources, and add them to your roles.

### Add System Permissions After an Upgrade

A deployment set up on an earlier release has a System resource server that declares only `system`. To add the other resources and actions, import the System resource server document from `bootstrap/01-default-resources.yaml` with the [import API](../../declarative-configurations/import-resources) and `options.upsert` set to `true`. Before you import it, set `identifier`, `name`, and `description` in the document to your System resource server's current values, and set `ouHandle` to the handle of the organization unit that owns it. The upsert overwrites these fields, so any value left at the bundled default replaces yours, and a different `ouHandle` moves the server to another organization unit.

The import adds the resources and actions that are missing and keeps the ones that already exist. Roles and assignments are not changed.

The sharing policy APIs require the `sharing` permissions, which `system:<resource>:view` and `system:<resource>:update` don't cover. If a role reads or changes sharing policies through those permissions, add the `sharing` permissions it needs, or `system:<resource>`, to the role. A role that holds `system` or `system:<resource>` keeps its access.

The import keeps your System resource server's existing delimiter. Check that it is `:` before you import, for example with `GET /resource-servers/{id}`. With any other delimiter, the imported permissions never match the ones the management APIs check.

## Create a Role

1. Navigate to **Roles** in the <ProductName /> Console and click **Create role**.
2. Enter a **Name** for the role. The name must be unique among the roles the selected organization unit owns and the roles shared with it.
3. Optionally enter a **Description**.
4. Select the **Organization unit** the role belongs to.
5. Select the **Permissions** to include by choosing a resource server and its actions.
6. Optionally add **Assignments** to immediately assign the role to users, groups, applications, or agents.
7. Click **Create**.

## List Roles

Navigate to **Roles** in the <ProductName /> Console to view all roles. The list shows each role's name, description, and organization unit.

Roles created from declarative configuration are marked as read-only and cannot be modified or deleted.

## Update a Role

1. Open the role from the **Roles** list.
2. Update the **Name**, **Description**, or **Permissions**.
3. Click **Save**.

:::warning
The update replaces the full set of permissions. Include every permission the role should keep: any permission omitted from the request is removed.
:::

## Delete a Role

1. Open the role from the **Roles** list.
2. Click **Delete** and confirm.

:::warning
Deleting a role also removes its assignments and revokes the role's scopes from the tokens its holders carry. See [Role Deletion](../protocols/oauth-oidc/token-revocation.mdx#role-deletion) for what is revoked and when a deletion is refused.
:::

## Manage Role Assignments

A role assignment grants the role's permissions to a principal. Principals can be users, groups, applications, or agents. When you assign a role to a group, all members of that group inherit the role's permissions.

| Assignee Type | Description |
|---------------|-------------|
| `user` | A user account. |
| `group` | A group. All current and future members inherit the role's permissions. |
| `app` | An application principal. |
| `agent` | An agent principal. |

### View Assignments

Open the role from the **Roles** list and select the **Assignments** tab to see all current assignments organized by type.

### Add Assignments

1. Open the role from the **Roles** list.
2. Select the **Assignments** tab.
3. Click **Add Assignments**.
4. Search for and select the users, groups, applications, or agents you want to assign.
5. Click **Add**.

### Remove Assignments

1. Open the role from the **Roles** list.
2. Select the **Assignments** tab.
3. Click **Remove** next to the assignment you want to delete and confirm.

### Mandated Assignments

A [user share can mandate](./manage-users.mdx#mandate-roles-on-a-shared-user) a role for a user in a child organization unit. A mandated assignment differs from a direct one in these ways:

- It appears in the role's assignments with `isReadOnly: true`.
- The organization unit cannot remove it. A removal that names only a mandated assignment fails with `ROL-1036`.
- A direct assignment of the same role to the same user in the same organization unit can exist beside it, and removing that direct assignment leaves the mandated one in place.
- It is not limited by the role's sharing rules. If the role is shared with the organization unit with assignments turned off, a mandate still applies there.

Two changes are refused with `409 Conflict` while a user share mandates the role:

| Change | Error |
|---|---|
| Unsharing the role from an organization unit where a user share mandates it | `ROL-1037` |
| Deleting the role | `ROL-1039` |

Remove the role from those user shares first, then repeat the change.

## Share a Role With Other Organization Units

A sharing policy makes a role available in organization units other than its own. It can reach the organization units beneath the role's organization unit, the top organization units of other trees, or both. An organization unit the role is shared with can assign the role to users, groups, applications, and agents, unless the policy turns assignments off there.

Create a sharing policy in one of three places:

- **The role's resource file**, in a `sharingPolicies` list.
- **Management API**, through the [Role Sharing API](../../apis.mdx#tag/role-sharing).
- **Console**, on the role's **Organization Access** tab.

To share a role from the Console:

1. Open the role from the **Roles** list.
2. Select the **Organization Access** tab.
3. Select whether only the role's own organization unit can use the role, or the organization units you choose. For chosen organization units, grant child organization units of the role's organization unit, top organization units of other trees, or both.
4. Click **Save changes**.

The Console cannot create a policy that reaches every organization unit in the deployment or the root of every other tree. Only a resource file or an import can set those. A policy that the role's resource file declares is read-only in the Console.

### Assignments Turned Off

A policy can turn assignments off for some of the organization units it reaches. Those organization units can use the role but cannot assign it. Only the role's resource file or the Role Sharing API can set this rule.

In the following resource file, the `acme-retail` organization unit can use the Auditor role but cannot assign it. The `acme-wholesale` organization unit and the organization units below it can assign the role, because assignments stay on unless a policy turns them off:

```yaml title="roles/auditor.yaml"
resource_type: role
id: auditor
name: Auditor
ouId: acme-root
permissions:
  - resourceServerId: reports-api
    permissions:
      - reports:read
sharingPolicies:
  - id: auditor-customers
    childUnits:
      mode: selected
      units:
        - ouId: acme-retail
          reach: unit
          overlayRules:
            assignments:
              editable: false
        - ouId: acme-wholesale
          reach: subtree
```

The same `overlayRules` block can sit on a whole section instead, such as `childUnits` with `mode: all`, to turn assignments off for every organization unit that section reaches. To set the rule through the API, see the [Role Sharing API](../../apis.mdx#tag/role-sharing).

The **Organization Access** tab shows where a policy turns assignments off, as a read-only note. When you save, the Console keeps the rule on every section and named organization unit that stays. A change that drops the rule asks you to confirm first, because the Console cannot turn assignments off again. For example, switching from all child organization units to selected ones drops a rule set on all child organization units.
