# Configuration

The <ProductName /> Next.js SDK reads configuration primarily from environment variables. This keeps secrets out of your source code and follows Next.js conventions.

## Environment Variables

Create a `.env` file in your project root:

```dotenv title=".env"
NEXT_PUBLIC_THUNDERID_BASE_URL=https://localhost:8090
NEXT_PUBLIC_THUNDERID_CLIENT_ID=<your-client-id>
THUNDERID_CLIENT_SECRET=<your-client-secret>
THUNDERID_SESSION_SECRET=<a-random-secret-for-session-encryption>
```

### Required Variables

| Variable | Description |
|----------|-------------|
| `NEXT_PUBLIC_THUNDERID_BASE_URL` | Your <ProductName /> instance URL. The `NEXT_PUBLIC_` prefix makes this available to client components |
| `NEXT_PUBLIC_THUNDERID_CLIENT_ID` | The Client ID from your <ProductName /> application |
| `THUNDERID_CLIENT_SECRET` | The Client Secret from your <ProductName /> application. Server-side only, never exposed to the browser |
| `THUNDERID_SESSION_SECRET` | A random string of at least 32 bytes that encrypts the session cookies. Generate one with `openssl rand -base64 32`. In production, the application refuses to start when it is missing or shorter. In development, the SDK uses a fixed fallback and logs a warning |

### Optional Variables

| Variable | Default | Description |
|----------|---------|-------------|
| `THUNDERID_SESSION_COOKIE_EXPIRY_TIME` | `86400` | Session cookie lifetime in seconds (24 hours by default) |

:::note
Earlier versions read the session secret from `THUNDERID_SECRET`. The SDK still reads it when `THUNDERID_SESSION_SECRET` is not set, and logs a warning to rename it. Earlier versions also signed the session cookie instead of encrypting it, so after the upgrade each user signs in again once.
:::

## Session Cookies

The SDK stores authentication state in encrypted, HttpOnly cookies. Each cookie is a JSON Web Encryption (JWE) value encrypted with `A256GCM`, using a key derived from `THUNDERID_SESSION_SECRET`, so the browser cannot read the tokens in it. A cookie that cannot be decrypted, for example after the secret changes, counts as no session.

| Cookie | Name in production | Name in development | `SameSite` | Lifetime | Purpose |
|--------|--------------------|---------------------|------------|----------|---------|
| Session cookie | `__Host-thunderid-session` | `thunderid-session` | `Strict`, or `Lax` with `THUNDERID_SESSION_COOKIE_SAME_SITE` | `THUNDERID_SESSION_COOKIE_EXPIRY_TIME` | Holds the access token, refresh token, ID token, user ID, scopes, the `sid` of the ID token, and the sign-in time |
| Sign-in cookie | `__Host-thunderid-session-state` | `thunderid-session-state` | `Lax` | 15 minutes, deleted when sign-in completes | Holds the sign-in in progress and the page to return to, so the callback can check its `state`. `Lax`, so it comes back on the redirect to the callback |

Every cookie is `HttpOnly`, on `Path=/`, with no `Domain`. In production it is also `Secure`, which the `__Host-` prefix requires.

A value larger than 4 KB is split across numbered cookies (`<name>.0`, `<name>.1`, and so on).

### Cookie Security Settings

| Setting | Value | Description |
|---------|-------|-------------|
| `httpOnly` | `true` | Prevents client-side JavaScript access |
| `secure` | `true` (production) | Requires HTTPS in production. A `Secure` cookie also takes the `__Host-` name prefix, so the browser keeps it to the host that set it, and a subdomain cannot set or overwrite it |
| `sameSite` | `strict` | Sends the session cookie only on requests your own site starts. Set `THUNDERID_SESSION_COOKIE_SAME_SITE=lax` to change it; see the warning below |
| `path` | `/` | Available to all routes |

:::warning
Setting `THUNDERID_SESSION_COOKIE_SAME_SITE=lax` deviates from RFC 10017. The browser then also sends the session cookie when the user follows a link to your app from another site. RFC 10017 recommends `strict` for a Backend for Frontend (BFF), so choose `lax` only when such links must land signed in, and the SDK logs a warning when you do. Cross-site request forgery is still refused by the SDK's request checks.
:::

## Application Configuration

Beyond environment variables, you can pass additional configuration to the `ThunderIDProvider`:

```tsx title="app/layout.tsx" showLineNumbers
import { ThunderIDProvider } from '@thunderid/nextjs/server'

export default function RootLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <html lang="en">
      <body>
        <ThunderIDProvider sessionCookieExpiryTime={3600}>
          {children}
        </ThunderIDProvider>
      </body>
    </html>
  )
}
```

## Key Differences from the React SDK

| Aspect | React SDK | Next.js SDK |
|--------|-----------|-------------|
| **Token storage** | Browser storage (sessionStorage, localStorage) | HttpOnly cookies (server-managed) |
| **Client type** | Public client (no secret) | Confidential client (with secret) |
| **PKCE** | Required | Not required (confidential client) |
| **Token refresh** | Client-initiated | Automatic in middleware |
| **Configuration** | Props on `ThunderIDProvider` | Environment variables |
