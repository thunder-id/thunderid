# Consent

<ProductName /> provides built-in support for capturing user consent during the login flow.

Consent can cover profile attributes, permissions, and [authorization details](#authorization-details-consent). For permission consent, place **Authorization** before **User Consent** in the sign-in flow. The consent screen lists the permissions the authenticated user holds for the requested resource; the issued token carries only the permissions they approve.

On a hierarchy-aware resource server, refusing a child permission also removes any remembered parent approval that covers it.

## Attribute Consent in Login Flows

When users authenticate with an application that requires specific profile attributes, <ProductName /> can prompt them to consent to sharing specific attributes with the application.

Attribute consent requirements are driven by the requested attributes during application configuration. If an application requires specific user attributes (e.g., username, email), the user will be asked to grant consent before the login process completes.

## Configuring Consent in Flows

The **User Consent** widget adds a pre-wired consent executor and consent screen and connects them into your flow automatically:

1. Navigate to the **Flows** section in the <ProductName /> console and select the flow you want to update (e.g., the default login flow).
2. In the flow builder, expand the **Widgets** section and add the **User Consent** widget. The consent screen and the **Allow** and **Deny** responses come pre-connected. The widget also connects its output to the **Auth Assert Generator** node and its input to the **Authorization** node when those are present in the flow. If either is missing, that edge is left open for you to connect to the node you want.
3. Save the flow configuration.

To assemble the consent step manually, add and connect the individual nodes instead:

1. In the flow builder, expand the **Executors** section and add the **User Consent** executor node. It should be placed after the necessary authentication steps and before the **Auth Assert Generator** node.
2. Connect the `onSuccess` edge of the preceding node to the input of the **User Consent** node, and then connect the `onSuccess` edge of the **User Consent** node to the next node in the flow (e.g., **Auth Assert Generator**).
3. Expand the **Steps** section and add the **Consent View** step to the flow. This step will render the consent page to the user during the login process.
4. Connect the `onIncomplete` edge of the **User Consent** node to the input of the **Consent View** step.
5. Then connect both **Allow** and **Deny** buttons in the **Consent View** step back to the **User Consent** node to handle user responses.
6. Save the flow configuration.

### Configure optional timeout for the user input

By default, the consent flow will wait indefinitely for the user to provide input. However, you can configure an optional timeout to end the prompt if the user does not respond within a specified time frame.

When the timeout expires, the prompt is submitted automatically as a denial. No consent decision is recorded, and the login completes without granting any of the requested attributes or permissions. This is not the same as denying an essential attribute, which terminates the login.

To set a timeout for user input in the consent flow:

1. In the flow builder, select the **User Consent** node.
2. In the node configuration panel, locate the **Consent Timeout** setting.
3. Enter the desired timeout duration in seconds (e.g., `60` for a 1-minute timeout).
4. Expand the **Components** section, and drag and drop the **Timer** component into the **Consent View** step.
5. Save the flow configuration.

### Fail the flow when the user denies consent

By default, the login flow still completes when the user clicks **Deny** on the consent prompt, as long as every requested attribute and permission is optional. Only a denial of an essential attribute or permission terminates the login on the default setting.

Enable **Fail flow when user denies consent** on the **User Consent** node when the flow must fail instead.

When enabled, the flow also fails if the consent prompt times out without a response.

To enable this setting:

1. In the flow builder, select the **User Consent** node.
2. In the node configuration panel, enable **Fail flow when user denies consent**.
3. Save the flow configuration.

### Configure validity period for granted consent

By default, once a user grants consent, it remains valid indefinitely until the user revokes it. However, you can configure a validity period for granted consent to require users to re-consent after a certain duration.

Currently, this configuration is supported via the Application Management API. When creating or updating an application, you can define the validity period under the `loginConsent` section in the JSON payload.

**Example request:**

```bash
curl --location -X POST 'https://localhost:8090/applications' \
--header 'Content-Type: application/json' \
--header 'Accept: application/json' \
--data '{
    "name": "Your Application Name",
    "template": "browser",
    "authFlowId": "019d206c-1766-76e2-aaa5-5b311dee8de7",
    "assertion": {
        "validityPeriod": 3600
    },
    "loginConsent": {
        "validityPeriod": 120
    }
}'
```

`validityPeriod` is specified in seconds (e.g., `120` for a 2-minute validity period). After this period expires, the user will be prompted to grant consent again during the next login attempt.

## Authorization Details Consent

When a client requests [intents](./intents.mdx) through the RFC 9396 `authorization_details` parameter, the **User Consent** step asks the user to approve each requested detail. See [Rich Authorization Requests](./protocols/oauth-oidc/rich-authorization-requests.mdx) for the request.

### Add the Steps to the Sign-in Flow

The default authentication flows have no consent step. When an application's flow has none, a sign-in that requests authorization details ends with `access_denied` and `Authorization details were not approved`.

Add these steps to the application's authentication flow, after the user signs in:

1. Add the **User Consent** widget, as described in [Configuring Consent in Flows](#configuring-consent-in-flows).
2. If a requested intent has a processor, expand the **Executors** section and add the **Check Intents** executor. Connect it after the node where the user signs in, and before **User Consent**, so that the processor approves or fills in each detail before the user sees it.
3. Save the flow configuration.

Without **Check Intents**, **User Consent** fails the flow with `FET-1130` when a requested intent has a processor. The client receives `access_denied` with `The sign-in flow does not run the checks the requested authorization details need`. An intent without a processor needs only **User Consent**. To define the steps in a flow definition instead, use the executors `AuthorizationDetailExecutor` and `ConsentExecutor`. See [Authorization and Consent](./flows/advanced-configurations.mdx#authorization-and-consent).

### The Consent Card

The consent screen shows one card for each detail that needs approval:

- The card heading is the intent's [consent summary](./intents.mdx#consent-summary), filled in with the requested values.
- Below it, the card lists the detail's fields with their display names. A value the processor supplied, such as an account number, appears as a value the user cannot edit.
- A field the intent lets the user change appears as an input: a number box, a date picker, or a list whose items the user can remove or add.
- Each card has its own **Approve** switch. A detail whose switch is off is left out of the grant.

### Narrow a Detail

The user can change a field only in the direction its [field policy](./intents.mdx#field-policies) allows, such as lowering an amount or removing an account from a list. The consent screen does not accept a wider value. For an amount of 45 that can only go down, entering 50 shows `Enter 45 or less.` and disables the approve action. The token carries the narrowed value.

<ProductName /> checks every change again when it records the decision. A change the intent does not allow fails the flow with `FET-1129`, and the client receives `access_denied` with `The change made to the authorization details is not allowed`.

### Deny

When the user clicks **Deny**, the flow goes on, as for attributes and permissions, and the token carries no authorization details. If **Fail flow when user denies consent** is enabled on the **User Consent** node, the flow fails instead. See [Fail the flow when the user denies consent](#fail-the-flow-when-the-user-denies-consent).

A processor that refuses every requested detail fails the flow before the consent screen with `FET-1127`, and a processor that cannot be reached fails it with `FET-1128`. See [Failures](./integrations/authorization-details-processor.mdx#failures).

### Earlier Approvals and New Versions

An intent with `reuse` set to `true`, that is, with **Ask every time** turned off, lets an earlier approval stand in. A request for a detail no wider than one the user already approved for the same application is not prompted again while the approval is within the application's [validity period](#configure-validity-period-for-granted-consent). A wider request is prompted. An intent with **Ask every time** turned on prompts on every request. A `prompt=consent` request, a CIBA request, and an application or agent with `loginConsent.alwaysPrompt` set to `true` also prompt every time.

An approval counts only for the intent version it was given on. A change to the intent's schema, consent summary, or reuse setting moves its version, and so does adding or removing its processor. The user is then prompted again on the next request. See [Versions](./intents.mdx#versions).

## Trying It Out

To verify the attribute consent flow using an application configured with consent requirements:

1. Ensure that the application is configured to request the necessary user attributes.
2. Start the login process for the application (e.g., by accessing the application's login page).
3. After successful authentication, you should be presented with the consent page, prompting you to grant or deny consent for sharing the requested attributes with the application.
4. Review the requested attributes and choose to either **Allow** or **Deny** consent.
5. If you allow consent, the login process will complete successfully, and the application will receive the approved attributes. If you deny any essential attributes, the login process will be terminated.
