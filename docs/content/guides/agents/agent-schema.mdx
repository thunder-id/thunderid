# Agent Schema

The agent schema defines the set of attributes every agent carries. There is one built-in schema, shared by all agents: it belongs to the single agent type, `default`, and <ProductName /> does not accept other agent types, so there is no per-agent-class schema. Each agent holds its own values for the attributes the schema defines. Attributes describe and classify an agent, for example which model it runs or what function it serves, and any attribute can be added to the agent's tokens for a downstream service to read.

The agent type has the handle `default` and the display name `Default`. The handle is the identifier that agents and applications use to refer to the agent type. It cannot be changed. The display name is free text and can be changed at any time.

## Why an agent has a schema

- **Consistent metadata.** Every agent is described by the same fields, so agents are classified and governed the same way across the organization.
- **Token claims.** Selected attributes are added to the agent's access token, so a resource can act on them, for example route by `modelProvider` or restrict by `function`.
- **Secrets.** An attribute marked as a credential is stored hashed and never returned, so an agent can carry a sensitive value without exposing it.

## Attributes an agent can have

Each attribute in the schema has:

- a **name** and a **display name**;
- a **type**: string, email, mobile, number, boolean, or enum;
- **required**: whether every agent must set a value;
- **unique**: whether the value must be unique across agents;
- **credential**: whether the value is stored hashed and hidden (string or number only);
- for a string, an optional **regex pattern**; for email or mobile, a **regex pattern** prefilled by the Console; for an enum, the list of **allowed values**.

Email and mobile attributes hold string values and support the **required** and **unique** flags. They cannot be credentials or define enum values. The Console requires a regex pattern for these types.

If an API request omits the pattern, the backend validates email addresses against `^[^\s@]+@[^\s@]+\.[^\s@]+$` and mobile numbers against `^\+[1-9]\d{1,14}$`. A custom pattern replaces the default. Agents do not support primary email or primary mobile mappings.

## The default schema

The built-in schema defines a required name and three optional attributes:

| Attribute | Type | Required | Values |
|---|---|---|---|
| `name` | string | Yes | A unique name for the agent |
| `modelProvider` | enum | No | `openai`, `anthropic`, `gemini`, `mistral`, `custom` |
| `model` | string | No | Free text, for example the model name |
| `function` | enum | No | `task-automation`, `rag-retrieval`, `code-gen`, `data-analysis`, `orchestrator`, `sub-agent`, `assistant`, `custom` |

Set these values in **Agent Details** during onboarding or on the agent's **Attributes** tab. API requests and declarative agent resources store the name in `attributes.name`. The schema controls its validation, just as it does for other attributes.

With the default schema, a missing name fails schema validation (`AGT-1015`), and a duplicate name causes an attribute conflict (`AGT-1014`). These errors apply to schema attributes, not to a separate agent-name field.

### Display attribute

The agent type's `systemAttributes.display` setting selects the schema attribute used as the agent's label in the Console. The default type selects `name`. This setting stores an attribute path, not the agent's name itself:

```yaml
systemAttributes:
  display: name
schema:
  name:
    type: string
    displayName: Name
    required: true
    unique: true
```

Set `systemAttributes.display` to another schema attribute to use that attribute as the label. Changing this setting does not rename attributes or change the schema's required and unique rules for `name`.

Agent get and list requests return the resolved `display` and `ouHandle` fields when called with `include=display`. If no display attribute is configured or its value is missing or empty, the label falls back to the agent ID. `display` is a read-only label, not a field to send when creating or updating an agent. The [import summary](../../declarative-configurations/import-resources#agent-resources) also resolves labels from the agent type's display setting.

### Collect attributes during onboarding

The schema defines the data an agent must have. The onboarding flow defines when and how an administrator supplies it. The Provisioning executor requests missing required attributes and can also request optional attributes with `includeOptional: true`. Enum attributes are offered as selections using the schema's allowed values.

When adding an attribute, add a field to the flow's attribute form or connect Provisioning's incomplete output to a dynamic input prompt. If a flow contains a manually configured selection, update its choices when changing the schema's enum values. See [Configure agent onboarding](../manage-agents#configure-agent-onboarding).

## Change the schema

- **Console:** click **Schema** on the **Agents** list. Add or edit attributes, set each one's type, display name, required, unique, and credential flags, a regex pattern (string, email, or mobile) or allowed values (enum), then save from the unsaved-changes bar.
- **API:** manage the schema through the agent-type endpoints. An update must send a `displayName`. The `handle` is optional. If sent, it must be `default`, otherwise the update fails with error `USRS-1014`. See the [Agent Types section of the API Reference](../../../apis#tag/agent-types).

Because the schema is shared by all agents, a change to it applies to every agent at once.
