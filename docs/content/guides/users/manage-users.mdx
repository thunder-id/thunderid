# Manage Users

A user in <ProductName /> represents an account that can authenticate with your applications. Each user has:

- A unique **ID** generated by <ProductName /> on account creation.
- A [user type](../user-types) (for example, `customer` or `employee`) that determines the profile attributes, validation rules, and registration settings for that user.
- A set of attributes that match the schema defined by their user type.
- An [organization unit](../../organization-units/manage-organization-units) that defines the user's place in the organizational hierarchy.

## Users and Organization Units

Every user belongs to an **Organization Unit (OU)** and has a **user type**. These two work together:

- The **user type** defines what the user looks like. Their attributes, constraints, and registration rules.
- The **organization unit** defines where the user belongs in the organizational hierarchy.

Each user type belongs to a specific OU. A user of that type can only be created under that OU or one of its descendants.

See [Organization Units](../../organization-units/manage-organization-units) for more information on how OUs structure your users and [User Types](../user-types) for how user types define attribute schemas and registration settings.

## Onboard a User

<ProductName /> uses a single **Add User** flow for both direct account creation and invite-based onboarding.

1. Navigate to **Users** in the <ProductName /> Console and click **Add user**.
2. Select a **User Type** to determine the user's attribute schema.
3. Select an **Organization Unit** that determines the user's position in the organization hierarchy.
4. Choose how to onboard the user:
   - **Create User**: Provision the user immediately by providing all required details and credentials.
   - **Invite User**: Generate an invite and let the user finish onboarding later.
5. Complete the remaining steps for the selected path.

When you create the account directly, provide the required user details and credentials, then submit the flow to provision the user immediately.

When you invite the user, enter the user's **Email** address and choose an invite method:

- **Send Invite Email**: <ProductName /> generates the invite and sends the email.
- **Get Invite Link**: <ProductName /> shows a copyable invite link that you can share with the user.

If the email service is unavailable, <ProductName /> still provides a copyable invite link so you can share it manually.

:::tip
The attributes available during onboarding depend on the selected user type. See [User Type Reference](../user-type-reference) to understand the defaults, or [User Types](../user-types) to create your own.
:::

## Update a User

1. Open the user from the **Users** list.
2. Edit the attributes you want to change.
3. To update group membership, add or remove groups on the **Groups** tab.
4. Click **Save**.

If the user type schema changed since the user was last saved, saving the user reconciles its stored attributes with the current schema:

- Values for attributes that were removed from the schema are discarded.
- Values for optional attributes that no longer conform to the schema are discarded.
- Values for required attributes that no longer conform to the schema must be corrected before the save can succeed.

Saving a different value for a verified email address or mobile number, or removing it, clears its verification. Changing the user type clears every verification the user has.

### Update User Credentials

Credential fields (such as passwords) are write-only and cannot be viewed. To set new credential values for a user:

1. Open the user from the **Users** list.
2. In the **Credentials** section, click **Update credentials**.
3. Fill in the credential fields you want to update. You do not need to update all credentials; empty fields are skipped.
4. Click **Save**.

## Suspend or Unlock a User

<ProductName /> locks a user's sign-in method automatically after repeated failed attempts, and the user's **Status** shows **Locked**. To end a user's access while you investigate, suspend the account. Suspending ends the user's sessions and revokes their tokens, and the record stays editable.

1. Open the user from the **Users** list.
2. Click **Actions**. Select **Suspend**, **Unsuspend**, **Unlock**, or **Unsuspend and unlock**. The menu offers only the operations that apply to the user's status.
3. Confirm the operation. **Unlock** runs without a confirmation.

For what each operation does, see [Suspend and Restore Accounts](../../account-protection/suspend-and-restore-accounts). For the lock policy and how a user recovers from a lock, see [Configure Account Lockout](../../account-protection/configure-account-lockout).

## Email Address and Mobile Number Verification

For a user that is not declarative (read-only), each top-level `email` or `mobile` attribute that holds a value and is not a credential shows a **Verified** or **Unverified** label on the user's **General** and **Attributes** tabs. Hover over **Verified** to see when the value was verified. The label describes the stored value, so the **Attributes** tab hides it while you edit that field. See [Attribute Types](../user-type-reference#attribute-types).

The Console only shows verification status. A signed-in user verifies their own email address or mobile number through a self flow that your application starts, for example from the profile component of a <ProductName /> SDK. See [Build a Flow](../../flows/build-a-flow#go-further).

User API responses that include a user's attributes also include `verifiedAttributes`: each verified attribute with the time it was verified, or an empty object when none is verified. The field is omitted when the server could not read the user's verification state, and from listings that return identifiers only.

Applications can receive the verification status in tokens and the UserInfo response as `<attribute>_verified`, for example `email_verified`, beside the attribute it describes. If the user type defines an attribute with that name, its stored value is released instead. See [Verified Contact Claims](../../protocols/oauth-oidc/claims-and-scopes#verified-contact-claims).

## Delete a User

1. Open the user from the **Users** list.
2. Click **Delete** and confirm.

:::warning
Deleting a user is permanent. The user's account, attributes, and group memberships are removed immediately.
:::

## Mandate Roles on a Shared User

A user can be [shared](../../key-concepts/resource-sharing.mdx) with the organization units beneath the one that owns it. A share can also mandate roles: for a child organization unit that the share names, it assigns the user the roles you list, in that organization unit.

A roles rule is accepted in one place only. It must sit on a unit listed under `childUnits` in `selected` mode, with `reach: unit`. A roles rule on `childUnits` in `all` mode, on `allUnits`, or on a unit with `reach: subtree` is refused with `USR-1039`.

```bash
curl -X POST https://localhost:8090/users/{userId}/sharing-policies \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "childUnits": {
      "mode": "selected",
      "units": [
        {
          "ouId": "acme-customer-a",
          "reach": "unit",
          "overlayRules": {
            "roles": {
              "editable": false,
              "value": ["<roleId>"]
            }
          }
        }
      ]
    }
  }'
```

The rule must set `editable` to `false` and list at least one role ID in `value`. Other shapes are refused:

| Rule | Error |
|---|---|
| `editable: true`, or `allowedValues` | `USR-1029`, because the rule would widen what the issuing organization unit holds. |
| No `value`, an empty `value`, or `excludedValues` | `USR-1040` |
| Roles on a server whose roles load only from resource files | `ROL-1038` |

Each role must also meet these requirements:

- The role is owned by, or shared with, the receiving organization unit. Otherwise the request fails with `ROL-1035`. <ProductName /> never shares the role for you.
- You hold every permission the role grants, the same rule as for adding a role assignment. Otherwise the request fails with `403 Forbidden` and the code `SAZ-4030`. See [Permission Requirements](./manage-roles.mdx#permission-requirements).

Mandating roles needs only the permission to manage users (`system:user`), not the permission to manage roles. An administrator who can share a user can therefore assign that user roles in the child organization units the share names, limited to roles that grant nothing the administrator lacks.

### How a Mandate Behaves

- Writing the share creates the mandated assignments in that organization unit. Updating the share brings them in line with the new list of roles, and deleting the share removes them.
- The child organization unit cannot remove a mandated assignment. It can still assign the same role to the same user directly, and it can remove that direct assignment. It can also add its own roles for the user.
- A role assignment response carries `isReadOnly: true` when the share mandates the assignment, and `isReadOnly: false` for a direct assignment.
- A share that the child organization unit makes onward can carry only roles from its own mandate.
- `GET /users/{id}/overlay-rules?ouId=<ouId>` returns the `roles` rule that applies to the asking organization unit.
- A role export leaves mandated assignments out, because they follow the share and would import back as direct assignments.

:::note
Removing a mandate does not revoke tokens that are already issued. The roles disappear from newly issued tokens. Removing a direct assignment through the REST API, by contrast, revokes the tokens that carry the role's permissions. See [Token Revocation](../protocols/oauth-oidc/token-revocation.mdx#role-assignment-removal).
:::

To import a user whose shares carry roles, put the user, the role, and the share in one import document. <ProductName /> replays the shares after the roles, so the document round-trips. See [Import Resources](../declarative-configurations/import-resources.mdx).
