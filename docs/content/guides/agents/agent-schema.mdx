# Agent Schema

The agent schema defines the set of attributes an agent carries. Each schema belongs to an agent type, and every agent is of one agent type. <ProductName /> ships one agent type, `default`, in the `default` organization unit. You can create more agent types, one per organization unit, to give a class of agents its own schema. Each agent holds its own values for the attributes its type's schema defines. Attributes describe and classify an agent, for example which model it runs or what function it serves, and any attribute can be added to the agent's tokens for a downstream service to read.

An agent type has a handle and a display name. The built-in agent type has the handle `default` and the display name `Default`. The handle is the identifier that agents and applications use to refer to the agent type. It is unique among agent types and cannot be changed. The display name is free text and can be changed at any time.

An organization unit can have only one agent type. Creating an agent type in an organization unit that already has one, or moving an agent type into such an organization unit, fails with error `USRS-1021`. When an agent is created, or an update changes its organization unit or type, the agent's organization unit must be its agent type's organization unit or one below it, otherwise the request fails with error `AGT-1049`. Moving an agent type to another organization unit does not move its agents or check them again. An agent type can be deleted only when no agent is of that type and no application, agent, or flow lists it in its allowed agent types; otherwise the deletion fails with error `USRS-1022`. Delete those agents or change their `type`, and remove the agent type from those lists, first.

## Why an agent has a schema

- **Consistent metadata.** Every agent is described by the same fields, so agents are classified and governed the same way across the organization.
- **Token claims.** Selected attributes are added to the agent's access token, so a resource can act on them, for example route by `modelProvider` or restrict by `function`.
- **Secrets.** An attribute marked as a credential is stored hashed and never returned, so an agent can carry a sensitive value without exposing it.

## Attributes an agent can have

Each attribute in the schema has:

- a **name** and a **display name**;
- a **type**: string, email, mobile, number, boolean, or enum;
- **required**: whether every agent must set a value;
- **unique**: whether the value must be unique across agents;
- **credential**: whether the value is stored hashed and hidden (string or number only);
- for a string, an optional **regex pattern**; for email or mobile, a **regex pattern** prefilled by the Console; for an enum, the list of **allowed values**.

Email and mobile attributes hold string values and support the **required** and **unique** flags. They cannot be credentials or define enum values. The Console requires a regex pattern for these types.

If an API request omits the pattern, the backend validates email addresses against `^[^\s@]+@[^\s@]+\.[^\s@]+$` and mobile numbers against `^\+[1-9]\d{1,14}$`. A custom pattern replaces the default. Agents do not support primary email or primary mobile mappings.

## The default schema

The built-in schema defines three optional attributes:

| Attribute | Type | Values |
|---|---|---|
| `modelProvider` | enum | `openai`, `anthropic`, `gemini`, `mistral`, `custom` |
| `model` | string | free text, for example the model name |
| `function` | enum | `task-automation`, `rag-retrieval`, `code-gen`, `data-analysis`, `orchestrator`, `sub-agent`, `assistant`, `custom` |

None are required, so an agent can set any, all, or none of them. Set the values per agent on the **Attributes** tab. See [Attribute values](../manage-agents#attribute-values).

## Change the schema

- **Console:** go to **Agent types** and open the agent type. On the **Schema** tab, add or edit attributes, set each one's type, display name, required, unique, and credential flags, a regex pattern (string, email, or mobile) or allowed values (enum), then save from the unsaved-changes bar.
- **API:** manage the schema through the agent-type endpoints. An update must send a `displayName`. The `handle` is optional. If sent, it must be the agent type's current handle, otherwise the update fails with error `USRS-1017`. See the [Agent Types section of the API Reference](../../../apis#tag/agent-types).

Because a schema is shared by every agent of its type, a change to it applies to all of those agents at once.

## Create an agent type

An organization unit can have one agent type. To create one in the Console:

1. Go to **Agent types** and click **Create agent type**.
2. If there is more than one organization unit, choose the one that owns the agent type and click **Continue**.
3. Enter a name. The Console suggests a handle from the name, which you can edit. You cannot change the handle after the agent type is created. Click **Continue**.
4. Add the attributes, choose the **Display attribute** that names agents of this type in listings, and click **Create agent type**.

If the organization unit already has an agent type, the Console shows an error. Choose another organization unit, or edit the existing agent type.

## Delete an agent type

1. Go to **Agent types** and open the agent type.
2. On the **Advanced** tab, click **Delete**, then confirm.

You can also click the delete icon on the agent type's row in the list. The delete is refused while agents are of the type, or while applications, agents, or flows list it in their allowed agent types. Delete or change those agents and remove the agent type from those lists first. A read-only agent type cannot be edited or deleted.
