# Notification Templates

A notification template is the content <ProductName /> sends to a user: the subject and body of an email, or the message body of an SMS. You manage templates while the server runs, from the Console or the Notification Templates API, and <ProductName /> stores them in its database. An edit takes effect on the next send, with no file to touch and no restart.

Each template belongs to a channel, `email` or `sms`, and carries a `handle` that a flow or an endpoint uses to pick it. A handle is unique within a channel, so a channel holds at most one template per handle. The content is not fixed text: it carries placeholders that <ProductName /> resolves when the message goes out, drawing on translations, the applicable design, and the values the flow produced.

## Prerequisites

- <ProductName /> is running. See [Get <ProductName />](../../../getting-started/get-thunderid).
- An access token with the `system:notificationtemplate` scope to change templates, or `system:notificationtemplate:view` to read them.
- For delivery, an [email provider](../email-providers) or [SMS provider](../sms-providers), selected on the flow's notification step.

## Channels and Handles

<ProductName /> looks up a template by its channel and handle, so a flow's notification step, and endpoints that send outside a flow, name the handle they want. The defaults ship for the notifications a deployment sends out of the box:

| Handle | Sent when | Channels |
| :--- | :--- | :--- |
| `otp` | A one-time passcode is issued for verification or sign-in. | email, sms |
| `user-invite` | An administrator invites a user to create an account. | email, sms |
| `self-registration` | A user starts self-registration and must confirm their address. | email, sms |
| `ciba-notification` | A backchannel (CIBA) request needs the user's approval. | email, sms |
| `magic-link` | A user signs in with a link instead of a password. | email |
| `password-recovery` | A user requests a password reset link. | email |

A handle can exist on one channel without the other, as `magic-link` and `password-recovery` do. If a flow asks for a channel and handle that has no template, the send fails; creating the template is what makes that combination available.

## Manage Templates

Templates live in the config database, and you work with them two ways.

In the Console, open **Customize → Notifications**, which splits into **Email Templates** and **SMS Templates**. From there you create a template with **New template**, open one to edit its display name, description, content, and, for email, its light or dark color scheme, preview the result, or delete it. A template a flow still references cannot be deleted. **Import / Export** moves templates as declarative resources for a GitOps workflow.

Over the API, manage templates under `/notification-templates/{channel}/templates`, where `{channel}` is `email` or `sms`:

| Method | Path | Description |
| :--- | :--- | :--- |
| `GET` | `/notification-templates/{channel}/templates` | List the channel's templates. |
| `POST` | `/notification-templates/{channel}/templates` | Create a template. |
| `GET` | `/notification-templates/{channel}/templates/{id}` | Read a template. |
| `PUT` | `/notification-templates/{channel}/templates/{id}` | Update a template. The handle does not change. |
| `DELETE` | `/notification-templates/{channel}/templates/{id}` | Delete a template, unless a flow references it. |

By default a template is a database row you can edit freely. If you would rather keep templates in version control, set `notification.template.store` to `declarative`, where templates come from files and the API and Console refuse writes with a `403`, or `composite`, where file-declared templates are read-only alongside editable database ones. See [Import Declarative Resources](../declarative-configurations/import-resources#notification-templates).

## Writing Template Content

An email template has a subject and a body; an SMS template has a body only. Each field is text with three kinds of placeholder, which <ProductName /> resolves in order, translations first, then design, then the runtime values:

- `{{t(key)}}` resolves to translated text, so one template serves every language. The key is read from the `notification` translation namespace.
- `{{design(token)}}` resolves a design token, such as `{{design(palette.primary.main)}}`, against the applicable theme. It is allowed only in an email body, never in a subject or in SMS.
- `{{ctx(key)}}` resolves to a value the sender supplies at send time, such as `{{ctx(otpCode)}}`.

The syntax is deliberately narrow, and its limits are worth knowing before you write a template:

- **Keys are case sensitive.** `{{ctx(otpCode)}}` resolves; `{{ctx(otpcode)}}` does not.
- **There are no filters, defaults, conditionals, or loops.** This is substitution, not a template language. Anything conditional belongs in a different template.
- **Rendering is fail-closed.** If a referenced translation key, a `{{design(...)}}` token, or a `{{ctx(...)}}` value cannot be resolved, <ProductName /> does not send the message and reports the error, rather than delivering it with a raw `{{...}}` left in place. A typo in a key name stops the send instead of reaching the user.

That last point is why the table below matters: a `{{ctx(...)}}` placeholder only resolves if something earlier produced its value, and referencing one that nothing supplies fails the send.

Content is also checked when you save it. A malformed or unsupported placeholder, or a `{{design(...)}}` token in a subject or in SMS, is rejected before the template is stored, so a template that could not render never reaches production.

### The Values a Sender Supplies

The runtime supplies these `{{ctx(...)}}` values:

| Key | Value |
| :--- | :--- |
| `appName` | Name of the application the flow is running for. |
| `otpCode` | The one-time passcode. |
| `expiryTime` | How long the code or link stays valid. |
| `magicLink` | The magic-link sign-in URL. |
| `inviteLink` | The invitation or recovery link. |
| `bindingMessage` | The CIBA binding message shown for approval. |

Which ones a template can use depends on its handle, because each handle's sender produces a different set:

| Handle | Values you can use |
| :--- | :--- |
| `otp` | `otpCode`, `expiryTime`, `appName` |
| `user-invite` | `inviteLink`, `appName` |
| `self-registration` | `inviteLink`, `appName` |
| `password-recovery` | `inviteLink`, `appName` |
| `magic-link` | `magicLink`, `expiryTime`, `appName` |
| `ciba-notification` | `inviteLink`, `appName`, `bindingMessage` |

The recurring surprise here is `inviteLink`. Password recovery, self-registration, and CIBA approval all deliver their link through the same invite executor, so the key is `inviteLink` in all of them. There is no `resetLink` or `approvalLink`.

`expiryTime` arrives already formatted for display, as a string such as `5 minutes` or `1 hour`, so you can drop it into a sentence without formatting it yourself.

In an HTML email body, <ProductName /> HTML-escapes each `{{ctx(...)}}` value before inserting it, so a value that contains `<` or `&` reads as text rather than markup. Translation and design results are content you authored, and are not escaped.

### Localizing and Theming

Because copy is written as `{{t(...)}}` keys rather than literal text, the same template renders in whatever language the `notification` translation namespace provides. Create and edit those keys from the editor's token panel or the Console **Translations** page. This phase renders in the system default language, `en-US`, and the Translation feature falls back to the nearest available value for a key; resolving each recipient's own language is an upcoming enhancement. For email, `{{design(...)}}` tokens resolve against the chosen theme and color scheme, so a template follows your branding without carrying a copy of it.

### The Standalone SMS OTP Endpoint

`POST /auth/otp/sms/send` renders the `otp` SMS template outside of any flow. Because no flow is running, there is no application, user, or identity provider to draw from, and the endpoint supplies only two values:

- `otpCode`
- `expiryTime`

Keep the `otp` SMS template to those two keys. Any other `{{ctx(...)}}` placeholder has nothing to resolve against, and because rendering is fail-closed, it stops the send.

## SMS Length

An SMS segment holds 160 characters. When a rendered SMS body exceeds that, <ProductName /> logs a warning and still sends the message; the provider then splits it into multiple segments, which most providers bill separately.

Write SMS bodies against the rendered length, not the template length. A body that looks short can grow well past 160 characters once a long `inviteLink` or a long `appName` is substituted in.
