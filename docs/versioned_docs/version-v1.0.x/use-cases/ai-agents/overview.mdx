# Understand It

A customer opens a travel application and asks its assistant to find flights for an upcoming trip. The
assistant searches and comes back with the options and their fares. The customer picks one and asks the
assistant to book it. The assistant searched on its own authority, then made the booking as the customer.

To the customer it is one conversation. To your backend, each of those steps raises the same set of questions:

- Who is acting?
- On whose authority?
- What is that authority allowed to reach?
- Can a service tell an agent working alone from an agent working for a person?

Answering those questions is what it takes to run agents you can account for, and the sign-in screen your
customer sees is a small part of it.

## The Problem

The first agent you ship usually borrows a credential from something else. The same problems surface as soon as
there is more than one of them:

- **Agents fit neither identity class.** An agent cannot work through a sign-in screen the way a person does,
  and it carries far more reach than the service accounts it gets pushed into. Give it a credential copied from
  either one and nothing in your traces tells you which agent made a call.
- **Whoever holds the credential is the agent.** It sits in your configuration and your container image, and a
  token lifted off the wire works for anyone who took it.
- **Authority has to be narrow.** An agent that may read a booking must not implicitly be able to cancel one,
  and the token it carries must not work against every API you run.
- **Acting for a person is not the same as being that person.** When an agent books a trip a customer asked
  for, the token has to name both of them, or you lose either the customer's consent or the record of which
  agent carried it out.
- **The agent is also something that gets called.** Its own endpoint needs the same authorization check as any
  other API you expose, so that not every signed-in user can reach it.
- **The person is not always there.** Work that runs on a schedule still reaches steps that need somebody's
  approval, with no browser to send them to.

## How It Works

Solving this gives the agent its own identity in a dedicated **identity layer**, and moves the authorization
decision out of the agent. The layer registers the agent as a principal, meaning something the layer can name
and issue tokens to, with a credential of its own. It holds the
roles that decide what the agent may reach, and it issues the token the agent presents on every call. Your
services read that token instead of trusting what the agent tells them.

<AgentSolutionArchitectureDiagram />

The token names a different principal in each case. When the agent works on its own, the token names the agent.
When it works for a customer, it names the customer as the subject and the agent as the actor, so one service
sees both at once. Each service verifies the token itself, or asks the identity layer whether it is still
valid, and authorizes the call against what the token carries.

:::tip Not Your Pattern?
- Your users sign in to a consumer application and no agent is involved: see
  [Secure Consumer Access to Your Application](../../b2c/).
- You are protecting a Model Context Protocol (MCP) server rather than an agent: see
  [Securing MCP](../mcp-authorization/overview).
:::

None of this is a proprietary protocol. It is standard [OAuth2 and OpenID Connect](../../../guides/protocols/oauth-oidc),
so the token your services already know how to verify is the token an agent presents. By the end of this
section you will have agents registered with their own credentials, roles that decide what each one may reach,
and APIs that authorize every call against the token it presents.
