# Configure an Email Provider

Create an email provider so that <ProductName /> can send magic links, user invitations, password recovery links, and other flow emails. An email provider is an `email-smtp` connection that stores an SMTP server's address, the sender identity, the transport security mode, and the credentials <ProductName /> authenticates with.

<ProductName /> has no deployment-wide email server. Each email step in a flow names the provider it sends through with the `senderId` node property, so a deployment can run several providers side by side. A flow whose email step names no provider cannot send email.

Create and manage email providers through the Connections API (`/connections/email-smtp`) or as declarative resources.

## Prerequisites

- Access to an SMTP server, such as Gmail, Amazon SES, SendGrid, or a self-hosted mail server, and its credentials if it requires authentication.
- An access token with the `system` scope for the API calls.

## Connection Fields

| Field | Required | Description |
|-------|----------|-------------|
| `name` | Yes | Display name of the connection. |
| `description` | No | Free-text description. |
| `host` | Yes | Hostname of the SMTP server, such as `smtp.example.com`. |
| `port` | Yes | Port of the SMTP server, from `1` to `65535`. Use `587` for STARTTLS or `465` for implicit TLS. |
| `fromAddress` | Yes | Email address used in the **From** header and as the SMTP envelope sender. Must be a valid email address. |
| `fromName` | No | Display name shown beside `fromAddress` in the **From** header, so a recipient sees `Acme Support <noreply@example.com>`. Without it, the header carries the bare address. Must not contain a line break. |
| `tls` | No | How the connection to the SMTP server is secured: `starttls`, `implicit`, or `none`. Defaults to `starttls`. See [Transport Security](#transport-security). |
| `authentication` | No | How <ProductName /> authenticates to the SMTP server. Omit it to send no credentials. See [Authentication](#authentication). |

`fromAddress` is always the envelope sender, whether or not you set `fromName`. Many relays accept mail only from an address or domain you have verified with them, so set `fromAddress` to a verified identity.

## Create an Email Provider

1. Send a `POST` request to `/connections/email-smtp` with the server details:

    ```bash
    curl -k -X POST https://localhost:8090/connections/email-smtp \
      -H "Authorization: Bearer $TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "name": "Corp SMTP",
        "host": "smtp.example.com",
        "port": 587,
        "fromAddress": "noreply@example.com",
        "fromName": "Acme Support",
        "tls": "starttls",
        "authentication": {
          "type": "basic",
          "properties": {
            "username": "mailer",
            "password": "<smtp-password>"
          }
        }
      }'
    ```

2. Copy the `id` from the response. This is the value you set as `senderId` on each email step.

    ```json
    {
      "id": "<email-provider-id>",
      "name": "Corp SMTP",
      "type": "email-smtp",
      "host": "smtp.example.com",
      "port": 587,
      "fromAddress": "noreply@example.com",
      "fromName": "Acme Support",
      "tls": "starttls",
      "authentication": {
        "type": "basic",
        "properties": {
          "username": "mailer",
          "password": "******"
        }
      }
    }
    ```

3. [Select the provider on each email step](#select-the-provider-on-an-email-step) of the flows that send email.

To list the email providers in a deployment, call `GET /connections/email-smtp`, or `GET /connections` with the `email-provider` category.

## Transport Security

The `tls` field selects how <ProductName /> secures the connection to the SMTP server:

| Mode | Behavior |
|------|----------|
| `starttls` | Default. Connects over plain TCP, then upgrades the connection with the STARTTLS command. If the server does not offer STARTTLS, the send fails rather than continuing in plaintext. Usually port `587`. |
| `implicit` | Opens a TLS connection directly (SMTPS). Usually port `465`. |
| `none` | Sends in plaintext. Use it only for a relay on a network you trust. |

Both TLS modes require TLS 1.2 or later and verify the server certificate against `host`.

<ProductName /> opens a new SMTP connection for each email. Establishing the connection times out after 30 seconds, and the whole SMTP exchange times out after 60 seconds.

## Authentication

The `authentication` object selects a method with `type` and carries that method's fields in `properties`. SMTP connections support two methods:

| Type | Properties | Behavior |
|------|------------|----------|
| `none` | None | Sends no credentials. This is the behavior when you omit `authentication`. |
| `basic` | `username`, `password` (both required) | Authenticates with SMTP PLAIN authentication. |

To list the supported methods and their fields from the server, call `GET /connections/meta?vendor=email-smtp`.

<ProductName /> rejects a connection that combines `tls: none` with an authentication method other than `none`, because the credentials would travel in plaintext.

### Credential Storage and Updates

<ProductName /> encrypts the password at rest and never returns it. Responses show the password as `******`.

To update a connection, send the full connection to `PUT /connections/email-smtp/{id}`. Omit `password` to keep the stored value. <ProductName /> keeps the stored password only while `host`, `port`, the authentication `type`, and `username` are unchanged. If you change any of them, supply the password again. Changing the authentication `type`, or setting it to `none`, discards the stored credentials.

## Select the Provider on an Email Step

The **Send Email** step (`EmailExecutor`) sends through the provider named by its `senderId` node property. Set `senderId` to the `id` of an email provider connection on every email step:

```json
{
  "id": "send_recovery_email",
  "type": "TASK_EXECUTION",
  "properties": {
    "senderId": "<email-provider-id>",
    "emailTemplate": "PASSWORD_RECOVERY"
  },
  "executor": {
    "name": "EmailExecutor",
    "mode": "send"
  },
  "onSuccess": "email_sent_status",
  "onFailure": "email_sent_status"
}
```

The flow designer's email step panel does not include a sender field. Set `senderId` in the flow definition through the Flow Management API (`/flows`) or in a declarative flow file.

The executor schema does not mark `senderId` as required, because the built-in flows declare their email steps before any provider exists. Sending still needs it:

- If `senderId` is missing or empty, does not match an existing connection, or names a connection that is not an email provider, the step fails with the flow error `FET-1038` (**Email provider is not configured**).
- If the SMTP server cannot be reached, rejects the credentials, or does not offer STARTTLS in `starttls` mode, the flow execution request fails with a server error.

For the full executor reference, see [Send Email](../../flows/advanced-configurations#executor-details-and-configuration).

## Declare an Email Provider as a Resource

An email provider can be a declarative resource with `resource_type: connection` and `type: email-smtp`. The fields match the API request body, plus an `id` that flows reference as `senderId`:

```yaml
resource_type: connection
id: 3f2b6c1e-8d4a-4c1e-9b7a-2d5e6f7a8b90
name: Corp SMTP
description: Transactional mail relay
type: email-smtp
host: smtp.example.com
port: 587
fromAddress: noreply@example.com
fromName: Acme Support
tls: starttls
authentication:
  type: basic
  properties:
    username: mailer
    password: "{{.CORP_SMTP_PASSWORD}}"
```

Keep the password out of the file with a template variable, and supply its value in the environment file you load with the resources. When you export an email provider, <ProductName /> writes each credential field as a template variable instead of its value.

<ProductName /> validates a declarative email provider when a step first sends through it. An invalid declarative provider causes a server error at that point.

For how to load declarative resources, see [Declarative Resources](../../../deployment/configuration#declarative-resources).

## Migrate From `email.smtp`

Earlier releases configured one SMTP server for the whole deployment in the `email.smtp` block of `deployment.yaml`, or under `configuration.email.smtp` in the Helm values. <ProductName /> no longer reads that configuration and does not migrate it automatically:

- A `deployment.yaml` that still contains an `email` block fails at startup, because <ProductName /> rejects unknown configuration fields.
- The Helm chart fails to render while `configuration.email` is set, with a message to create an email provider connection instead.

To migrate:

1. Create an email provider connection from your previous values, using the mapping below.
2. Set `senderId` to the new connection's `id` on every email step in every flow that sends email, including flows created from built-in templates.
3. Remove the `email` block from `deployment.yaml`, or `configuration.email` from your Helm values, then restart or upgrade.

On Kubernetes, the chart no longer creates the `smtp-password` key or injects `SMTP_PASSWORD`. If you referenced your own Secret with `passwordRef`, supply that password in the connection instead, then delete the Secret when nothing else uses it.

| `deployment.yaml` key | Helm value | Connection field |
|-----------------------|------------|------------------|
| `email.smtp.host` | `configuration.email.smtp.host` | `host` |
| `email.smtp.port` | `configuration.email.smtp.port` | `port` |
| `email.smtp.from_address` | `configuration.email.smtp.fromAddress` | `fromAddress` |
| `email.smtp.username` | `configuration.email.smtp.username` | `authentication.properties.username` |
| `email.smtp.password` | `configuration.email.smtp.password` or `passwordRef` | `authentication.properties.password` |
| `email.smtp.enable_authentication: true` | `configuration.email.smtp.enableAuthentication: true` | `authentication.type: basic` |
| `email.smtp.enable_authentication: false` | `configuration.email.smtp.enableAuthentication: false` | `authentication.type: none`, or omit `authentication` |
| `email.smtp.enable_start_tls: true` | `configuration.email.smtp.enableStartTls: true` | `tls: starttls` |
| `email.smtp.enable_start_tls: false` | `configuration.email.smtp.enableStartTls: false` | `tls: none` |

The old configuration accepted authentication without STARTTLS. A connection rejects that combination, so either set `tls` to `starttls` or `implicit`, or set the authentication `type` to `none` for a relay that needs no credentials.

A connection also supports settings the old block did not have: `fromName`, and `tls: implicit` for SMTPS on port `465`.
