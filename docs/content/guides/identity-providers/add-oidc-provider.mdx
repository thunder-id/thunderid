# Add an OIDC Identity Provider

This guide explains how to register a generic OpenID Connect (OIDC) identity provider (IdP) in <ProductName />. Use this type for any standard OIDC-compliant provider.

## Prerequisites

- <ProductName /> is running. See [Get Started](../../../getting-started/get-thunderid).
- You can sign in to the <ProductName /> Console.
- A client application registered in the external OIDC provider with a **Client ID** and **Client Secret**, and permission to add the **Redirect URI** shown by the Console.

:::tip Finding endpoint URLs
Most OIDC providers publish their endpoint URLs in a discovery document at:

```text
https://<provider-domain>/.well-known/openid-configuration
```

Open this URL in a browser to find the `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint`, `jwks_uri`, and `issuer` values.
:::

## Create the OIDC Connection

<Stepper stepNode="h3" as="h3">

### Step 1: Add a Custom Connection

1. Sign in to the <ProductName /> Console.
2. Navigate to **Connections**.
3. Click the **Add custom connection** card.

### Step 2: Choose the Connection Type

1. On the **Connection type** step, click **OpenID Connect Provider**.
2. Click **Continue**.

### Step 3: Name the Connection

1. Enter a **Connection name**, or pick one of the suggested names.
2. Click **Continue**.

### Step 4: Configure the Connection

The form shows a setup hint with the **Redirect URI**. Before creating the connection, copy it and register it as the callback URL with your OIDC provider.

Enter the following fields, then click **Create connection**:

| Field | Required | Description |
|-------|----------|-------------|
| **Client ID** | Yes | The client ID issued by the OIDC provider. |
| **Client secret** | Yes | The client secret issued by the OIDC provider. |
| **Authorization endpoint** | Yes | The provider's authorization endpoint, used to start the sign-in flow. |
| **Token endpoint** | Yes | The provider's token endpoint, used to exchange the authorization code for tokens. |

</Stepper>

Optional settings are not part of the creation wizard. After creation, open the connection and configure them on its edit page:

| Field | Description |
|-------|-------------|
| **UserInfo endpoint** | The provider's userinfo endpoint. Used to fetch additional profile claims. |
| **JWKS endpoint** | The URL of the provider's JSON Web Key Set. Required when **Enable token exchange** is on. |
| **Issuer** | The provider's issuer identifier, expected in tokens from this provider. Required when **Enable token exchange** is on. |
| **Scopes** | Space-separated OIDC scopes to request. Defaults to `openid email profile` if left blank. |
| **Prompt** | Optional prompt value forwarded to the provider's authorization request, for example `select_account` or `consent`. |

Under **Federation**, turn on **Enable token exchange** to accept subject tokens from this provider for token exchange. This makes **Issuer** and **JWKS endpoint** required, and reveals an optional **Trusted token audience** field, the accepted audience value for external tokens during token exchange.

## Attribute Configuration

External providers emit attributes under their own names, which may differ from the attribute names <ProductName /> uses locally (for example, a provider may emit `given_name` where your user type defines `firstName`). Open the connection and go to the **Attribute Configuration** tab to map external attributes to local user attributes.

### User Type Resolution

By default, every federated identity resolves to the connection's **Default User Type**. To derive the user type from an incoming claim instead, turn on **Resolve user type from an attribute** and set the attribute whose value decides the user type (for example, `user_type`; supports dot notation for nested claims, for example `profile.role`).

Under **Value Mapping**, map each external attribute value to a local user type (for example, `staff` to `Employee`, `partner` to `Contractor`) using **Add Value**. The **Default User Type** remains the fallback used when the claim is missing or its value has no mapping.

The resolved user type selects which mapping set applies under **Attribute Mappings**.

### Attribute Mappings

Click **Add User Type** to add a mapping set for a user type, then click **Add Mapping** to add attribute mappings within that set. Each mapping has:

| Field | Description |
|-------|-------------|
| **External Attribute** | The external attribute name (for example, `given_name`). |
| **Local Attribute** | The target local attribute (for example, `firstName`). Must be an attribute defined in that user type's schema. |

Behavior:

- The external attribute supports complex forms. Use **dot notation** to read a value nested inside another attribute. For example, `email.work` reads the `work` field from an `email` object.
- The local attribute must be defined in the user type's schema; this is validated when you save the connection.
- Mappings copy rather than rename: the mapped value is published under the local attribute, and the original attribute is kept under its own name. Attributes without a mapping pass through unchanged.

The mapping applies both when a user signs in through this connection in an authentication flow and when a token from this provider is exchanged (see [Trusted Issuer](../../trusted-issuer)). The resulting local attributes flow into the issued access and ID tokens, subject to the application's `userAttributes` configuration.

### Authorization Mapping

Map attribute values this provider asserts, such as group membership, onto local roles, groups, or permissions, under **Authorization Mapping**. Click **Add Mapping** to add a mapping for a claim, then choose how its values resolve:

- **Direct** (the default): each value the claim asserts is looked up by name against an existing role, group, or permission of the chosen **Target Type**. A value with no exact match, or more than one, confers nothing.
- **Advanced**: turn the mapping's toggle on to compare the claim's values against an explicit rule table instead of matching by name.

| Field | Description |
|-------|-------------|
| **Key** | The claim to read (for example, `groups`). Supports dot notation for a nested claim. |
| **Value Type** | Advanced only. How to interpret the claim's value(s): `String`, `Number`, `Boolean`, or `Array`. Defaults to `String`. |
| **Delimiter** | Splits a string claim into multiple values (for example, a space-delimited scope string). Leave unset for a single value. Only applies when Value Type is `String`. |
| **Operator** | Advanced only, per rule. `Equals`/`Not Equals` for a single value; `Greater Than`/`Less Than`/`Greater Than or Equal`/`Less Than or Equal` when Value Type is `Number`; `Includes`/`Not Includes` when the claim carries a set of values (an `Array`, or a `String` split by Delimiter). |
| **Target Type** | Direct only. Whether each value is looked up as a `Role`, `Group`, or `Permission`. A `Permission` target also requires a **Resource Server**. |

Behavior:

- An advanced rule's targets can span roles, groups, and permissions across more than one resource server at once.
- A mapped group also grants that group's ancestor groups, transitively, the same as a direct group assignment does.
- Everything a mapping grants adds to whatever is already assigned directly; it never replaces it.
- The mapping applies wherever the identity's attributes are read: at sign-in, when a token from this provider is exchanged, and when an identity assertion (ID-JAG) it issued is presented. If resolving the mapping fails, sign-in still proceeds without it; token exchange and ID-JAG consumption fail the request instead, since there is no already-issued session to fall back to.
- To also assign a mapping's roles and groups the moment an account is first created, rather than only computing them at each sign-in, enable **Seed Groups/Roles From Authorization Mapping** on the flow's Provisioning step. See [Provisioning](../../flows/advanced-configurations#user-provisioning-and-attributes).

### Account Linking

To match an incoming federated identity that has no recorded link to an existing local user by attributes, add attributes under **Account Linking**. Click **Add Attribute** to add an external attribute (for example, `email`) that is matched to find the associated local user.

Behavior:

- Resolution tries the recorded link for this connection and subject first. A subject is unique only within the connection that issued it, so both parts are required and a subject on its own never resolves a user.
- Otherwise, every configured attribute that has a value must match. Each local user that matches becomes a candidate. A match does not sign the user in: the flow's Account Linking node has the user verify one of the candidates before linking it. The direct authentication API cannot prompt, so it signs in recorded links only.
- Each attribute is an external claim name. It matches on every local attribute it's mapped to under **Attribute Mappings**, and on the local attribute of the same name, because mappings copy the value there too. For example, with `email` mapped to `username`, linking on `email` finds a user whose `username` or whose `email` holds the incoming address.
- Each local attribute is matched on the value it would be provisioned with. An attribute with no mapping of its own therefore also works as a local attribute name: linking on `costCenter` with `cost_centre` mapped to `costCenter` matches on the incoming `cost_centre` value.
- The same-named local attribute is skipped when its name has characters other than letters, digits, and underscores, which includes dot notation, and for a mapped attribute when another attribute is mapped onto that name. If a configured attribute has a value but nothing to match on, the connection matches no one.
- `userID`, `federatedIdpId`, `credentialUpdatedAt`, and `linkedIds` are reserved and never matched on. Saving rejects a linking attribute that is, or is mapped to, one of them.
- If the configured attributes match more than one user, including when two of an attribute's local attributes name different users, every matching user is a candidate. The user verifies whichever account is theirs, and that account is the one linked.
- If more than 10 users match, the sign-in fails. An attribute that matches that many users does not identify a person, so treat it as a configuration error.
- If nothing resolves a user, the user is treated as new (subject to the flow's provisioning configuration).
- Once a flow resolves or provisions the user, it records the link. Later sign-ins through this connection resolve on that link and never consult the attributes again.

Click **Save changes** to apply your attribute configuration.
