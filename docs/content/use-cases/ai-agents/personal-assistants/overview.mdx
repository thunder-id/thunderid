# Let Customers Bring Their Own Personal Agent

A bank customer uses a personal agent, an AI agent that handles their everyday chores. Each week they ask it to check
their balance, list the week's card payments, and point out anything unusual. To do that, the agent has to call
the bank's APIs as that customer.

To the customer, it is their agent running one more errand. To the bank, it is an agent it has never seen
before, brought in by a customer and asking to act with that customer's access. The bank did not build it and needs
no arrangement with whoever did, so what it trusts about the agent has to come from the customer who brought it.

## The Problem

The bank is one example. Any organization whose customers sign in to use its services meets the same problem once
those customers start bringing their own personal agents, whether it runs a bank, an insurer, or a utility. Each time
such an agent calls an API, the same identity questions come up:

- **Whose agent is it?** The customer brings the agent in, not the bank. It has to belong to that customer
  from the moment it is registered, and stay theirs.
- **For whom can it act?** Only its customer. It must not reach another customer's account, and it must not act on
  its own authority with nobody behind it.
- **Who decides what it may do?** The customer approves what the agent asks for, and can approve less. A
  permission the customer does not hold is never theirs to give.
- **Who made the call?** The bank's APIs need to see both the customer whose account is used and the agent that
  made the request, so an action the agent took is never mistaken for one the customer took themselves.
- **How is it stopped?** The customer needs to pause or remove the agent. The bank needs to stop it too, for
  example when a flaw is reported in it, without locking the customer out of their own account.
- **What can the bank see?** The bank's security team needs to find every agent its customers have registered,
  and know whose each one is.

These all come back to one requirement:

> **An agent a customer brings in needs an identity of its own, tied to that customer.**

## How It Works

The identity layer registers the agent as an identity of its own, owned by the customer who brought it in. It
issues the agent tokens only for that customer, and only after the customer signs in and approves.

<PersonalAssistantSolutionDiagram />

The customer registers the agent once, as their own (1). When the agent needs access, it asks the identity
layer (2). The identity layer asks the customer to sign in and approve what the agent asks for (3), then issues a
signed token for that customer only and returns it to the agent (4). The agent sends the token with each
call, and the bank's APIs check it (5).

The token names the customer as the subject and the agent as the actor, so the APIs apply the customer's
permissions and still know the agent made the request. Once the customer allows it, the agent can renew its access
without the customer signing in again, and each renewed token still names both.

Control is shared by the two parties that answer for the agent. The customer can change how it gets access, pause
it, or remove it. The bank can find any agent and stop it, and when a customer's own account is suspended or
closed, their agents stop with it.
