# Manage Users

A user in <ProductName /> represents an account that can authenticate with your applications. Each user has:

- A unique **ID** generated by <ProductName /> on account creation.
- A [user type](../user-types) (for example, `customer` or `employee`) that determines the profile attributes, validation rules, and registration settings for that user.
- A set of attributes that match the schema defined by their user type.
- An [organization unit](../../organization-units/manage-organization-units) that defines the user's place in the organizational hierarchy.

## Users and Organization Units

Every user belongs to an **Organization Unit (OU)** and has a **user type**. These two work together:

- The **user type** defines what the user looks like. Their attributes, constraints, and registration rules.
- The **organization unit** defines where the user belongs in the organizational hierarchy.

Each user type belongs to a specific OU. A user of that type can only be created under that OU or one of its descendants.

See [Organization Units](../../organization-units/manage-organization-units) for more information on how OUs structure your users and [User Types](../user-types) for how user types define attribute schemas and registration settings.

## Onboard a User

<ProductName /> uses a single **Add User** flow for both direct account creation and invite-based onboarding.

1. Navigate to **Users** in the <ProductName /> Console and click **Add user**.
2. Select a **User Type** to determine the user's attribute schema.
3. Select an **Organization Unit** that determines the user's position in the organization hierarchy.
4. Choose how to onboard the user:
   - **Create User**: Provision the user immediately by providing all required details and credentials.
   - **Invite User**: Generate an invite and let the user finish onboarding later.
5. Complete the remaining steps for the selected path.

When you create the account directly, provide the required user details and credentials, then submit the flow to provision the user immediately.

When you invite the user, enter the user's **Email** address and choose an invite method:

- **Send Invite Email**: <ProductName /> generates the invite and sends the email.
- **Get Invite Link**: <ProductName /> shows a copyable invite link that you can share with the user.

If the email service is unavailable, <ProductName /> still provides a copyable invite link so you can share it manually.

:::tip
The attributes available during onboarding depend on the selected user type. See [User Type Reference](../user-type-reference) to understand the defaults, or [User Types](../user-types) to create your own.
:::

## Update a User

1. Open the user from the **Users** list.
2. Edit the attributes you want to change.
3. To update group membership, add or remove groups on the **Groups** tab.
4. Click **Save**.

If the user type schema changed since the user was last saved, saving the user reconciles its stored attributes with the current schema:

- Values for attributes that were removed from the schema are discarded.
- Values for optional attributes that no longer conform to the schema are discarded.
- Values for required attributes that no longer conform to the schema must be corrected before the save can succeed.

Saving a different value for a verified email address or mobile number, or removing it, clears its verification. Changing the user type clears every verification the user has.

### Update User Credentials

Credential fields (such as passwords) are write-only and cannot be viewed. To set new credential values for a user:

1. Open the user from the **Users** list.
2. In the **Credentials** section, click **Update credentials**.
3. Fill in the credential fields you want to update. You do not need to update all credentials; empty fields are skipped.
4. Click **Save**.

### Ask a User to Reset a Credential

To have a user choose a new password, PIN, or other credential themselves, without you setting or seeing it, start a credential reset. <ProductName /> emails the user a reset link at the email address on their profile, then removes the current credential and signs the user out everywhere. Once the reset starts successfully, the current credential no longer works. If the reset fails after the email is sent, the emailed link stops working. The current credential may already be removed, so start another reset. The user opens the link, in any browser and without signing in, and sets the new value.

<ProductName /> ships the `default-admin-user-credential-reset-flow` flow for this. Its **Send Email** step ships without an email provider, so select your provider on that step and save the flow before you start a reset. The flow sends the link to the profile attribute that step's email input names, `email` by default. See [Configure an Email Provider](../../notifications/email-providers).

To start a reset in the Console, open the user and go to the **Credentials** tab. Click the credential's reset button, such as **Reset Password**. In the dialog, choose **Email the user a link to set a new password**, then click **Send reset link**. The Console starts the flow that `adminUserCredentialResetFlow` names in the `flow` server configuration section, the shipped flow by default. The dialog offers the link only for text credentials, and only when:

- You can update users and read the server configuration.
- A flow is set for `adminUserCredentialResetFlow`. See [Flow Defaults](../../../deployment/configuration#flow-defaults).
- The Console runs user administration through flows.
- The user is not declarative (read-only).

For a suspended user or an expired account, the link option is disabled, and the dialog says why. You can still set a new value there. A locked user can still be sent a link.

To build a flow of your own, create an **Administrator-initiated** flow from the **Administrator User Credential Reset with Email Link** template. Select its email provider on the **Send Email** node and save the flow, then set `adminUserCredentialResetFlow.defaultHandle` to its handle. The **Operation** setting of each credential node selects what it does: **Validate credential reset**, **Remove credential**, or **Set credentials**. See [Build a Flow](../../flows/build-a-flow#go-further) and [Credential Verification and Management](../../flows/advanced-configurations#credential-verification-and-management).

To start the flow through the Flow Execution API instead, use an administrator access token that carries `system:user:update` or `org:user:update`. Name the user's ID in the `subject` input and the credential to reset in the `credential` input:

```bash
curl -kL -X POST https://localhost:8090/flow/execute \
  -H "Authorization: Bearer $ADMIN_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "flowType": "ADMIN_INITIATED", "handle": "default-admin-user-credential-reset-flow", "inputs": { "subject": "<user-id>", "credential": "password" }, "verbose": true }'
```

The credential must be a text credential that the user's type declares, such as `password` or `pin`. Keep `"verbose": true`: the start decides it for the whole flow, and the page the link opens shows the form only in verbose mode. Without the `credential` input, the response asks for it. Once the email is sent, the response has `"flowStatus": "INCOMPLETE"` and `additionalData.emailSent` set to `"true"`. The response never contains the link. The flow runs with your permissions, so you can reset only users you can update. The link goes to the address on the user's profile, even when `inputs` carries another, such as `email`. See [Build a Flow](../../flows/build-a-flow#go-further) and the [Flow Execution API](../../../apis#tag/flow-execution).

A reset is refused, and the current credential keeps working, when the user has no email address in the attribute the flow sends to, when the email cannot be sent, or when the user is suspended or their account has expired. A locked user can still be reset, and the default flow releases the lock once the user sets the new value. The link expires with the flow, 6 hours by default (`adminInitiatedFlow.expirySeconds`). An expired link does not restore the old credential, so start another reset. A later reset voids an earlier link once it removes the credential, and so does a forgot password recovery or any other change to a credential the user's type declares, such as a password or PIN. A later reset that is refused before it removes the credential, or adding a passkey, leaves the earlier link working.

## Suspend or Unlock a User

<ProductName /> locks a user's sign-in method automatically after repeated failed attempts, and the user's **Status** shows **Locked**. To end a user's access while you investigate, suspend the account. Suspending ends the user's sessions and revokes their tokens, and the record stays editable.

1. Open the user from the **Users** list.
2. Click **Actions**. Select **Suspend**, **Unsuspend**, **Unlock**, or **Unsuspend and unlock**. The menu offers only the operations that apply to the user's status.
3. Confirm the operation. **Unlock** runs without a confirmation.

For what each operation does, see [Suspend and Restore Accounts](../../account-protection/suspend-and-restore-accounts). For the lock policy and how a user recovers from a lock, see [Configure Account Lockout](../../account-protection/configure-account-lockout).

## Email Address and Mobile Number Verification

For a user that is not declarative (read-only), each top-level `email` or `mobile` attribute that holds a value and is not a credential shows a **Verified** or **Unverified** label on the user's **General** and **Attributes** tabs. Hover over **Verified** to see when the value was verified. The label describes the stored value, so the **Attributes** tab hides it while you edit that field. See [Attribute Types](../user-type-reference#attribute-types).

To ask a user to verify an unverified email address, the Console starts the flow named by `adminAttributeVerificationFlow` in the `flow` server configuration section, the shipped `default-admin-attribute-verification-flow` by default. That flow's **Send Email** step ships without an email provider, so first select your provider on that step and save the flow. Edit the flow to change the email or the steps, or point the setting at your own flow; see [Build a Flow](../../flows/build-a-flow#go-further) and [Flow Defaults](../../../deployment/configuration#flow-defaults).

Then open the user's **Attributes** tab and select **Verify** in that email field. <ProductName /> emails the user a link, and the address shows **Verified** once the user opens the link and confirms. You can send a link only when:

- You can update users and read the server configuration.
- A flow is set for `adminAttributeVerificationFlow`.
- The Console runs user administration through flows. Otherwise it shows the status only.
- The address is saved. After you change an address, save the user first.
- The user is not suspended and their account has not expired. A locked user can still be sent a link.

Mobile numbers cannot be sent a link from the Console.

In the <ProductName /> SDK profile, a signed-in user selects **Verify** beside a saved email address or mobile number to start the self-service flow. See [Build a Flow](../../flows/build-a-flow#go-further).

User API responses that include a user's attributes also include `verifiedAttributes`: each verified attribute with the time it was verified, or an empty object when none is verified. The field is omitted when the server could not read the user's verification state, and from listings that return identifiers only.

Applications can receive the verification status in tokens and the UserInfo response as `<attribute>_verified`, for example `email_verified`, beside the attribute it describes. If the user type defines an attribute with that name, its stored value is released instead. See [Verified Contact Claims](../../protocols/oauth-oidc/claims-and-scopes#verified-contact-claims).

## Let Users Change Their Own Account

A signed-in user reads and changes their own account through the self-service APIs, with an access token issued to that user. Reading the account with `GET /users/me` and changing attributes other than an email address or mobile number with `PUT /users/me` need only a valid user access token. The changes in the following table also need a self-service permission of the System resource server and a recent sign-in.

| Permission | Change | API |
|------------|--------|-----|
| `self:credentials:update` | Set the user's own credentials, such as a password or PIN | `POST /users/me/update-credentials` |
| `self:agentcredentials:update` | Set the credentials of a personal agent the user owns | `POST /users/me/agents/{id}/update-credentials` |
| `self:protectedattributes:update` | Add, change, or remove an attribute of type `email` or `mobile` | `PUT /users/me` |

### Request a Self-Service Permission

Every user holds the self-service permissions without a role. An access token carries one only when the application asks for it: name the permission in `scope` and the System resource server in `resource`. In a default deployment, the System resource server's identifier is `https://localhost:8090/mcp`. <ProductName /> does not yet limit which applications can ask for these permissions.

An access token binds one resource server, so a token issued for your own API cannot also carry a self-service permission. Request a separate token for the self-service call, for example when the user opens the page that changes the password:

```http
GET /oauth2/authorize
  ?response_type=code
  &client_id=$CLIENT_ID
  &redirect_uri=https://app.example.com/callback
  &scope=self:credentials:update
  &resource=https://localhost:8090/mcp
  &code_challenge=$CODE_CHALLENGE
  &code_challenge_method=S256
  &state=$STATE
```

Name the same `resource` when you redeem the code. See [Resource Indicators](../protocols/oauth-oidc/resource-indicators.mdx).

If you set `server.security.system_permission_prefix`, the APIs expect the prefixed permissions, for example `mgmt:self:credentials:update`. Users then hold them through roles on your own resource server, like the other prefixed system permissions, and the `maxAge` still comes from the action on the System resource server.

### Recent Sign-In

Each self-service action on the System resource server sets a `maxAge`, the number of seconds a sign-in stays recent enough for the change. All three ship with `maxAge: 300`. To change it, update the action through the resource server API, as described in [Update an Action](../resource-servers.mdx#update-an-action).

The API compares `maxAge` with the access token's `auth_time` claim, the time the user signed in. Access tokens issued by the authorization code, CIBA, and device authorization grants carry `auth_time`, and so do tokens from a token exchange of the assertion a sign-in flow returns. A refreshed access token keeps the original `auth_time`, so refreshing a token does not make the sign-in recent again. See [`max_age` and `auth_time`](../protocols/oauth-oidc/openid-connect.mdx#max_age-and-auth_time).

The API answers a self-service change as follows:

| Token | Response |
|-------|----------|
| Does not carry the permission | `403`. The code is `AUTH-4030` on the two credential APIs and `USR-1047` on `PUT /users/me`. |
| Carries the permission, and the sign-in is older than `maxAge` or the token has no `auth_time` | `401` with the code `AUTH-4011` and a `WWW-Authenticate` challenge. |
| Carries the permission, and the sign-in is within `maxAge` | The change is made. |

The challenge follows [RFC 9470](https://datatracker.ietf.org/doc/html/rfc9470):

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="insufficient_user_authentication", error_description="A more recent authentication is required", max_age="300"
```

The `/users/me` APIs list `WWW-Authenticate` in `Access-Control-Expose-Headers`, so a browser application can read the challenge.

### Handle the Challenge

When a self-service call returns the `insufficient_user_authentication` challenge, sign the user in again and retry:

1. Read `max_age` from the `WWW-Authenticate` header.
2. Send a new authorization request with `max_age` set to that value, or with `prompt=login`. Keep the same `scope` and `resource`.
3. Redeem the code, then retry the call with the new access token.

Refreshing the old token does not help, because the refreshed token keeps the original `auth_time`. `max_age` and `prompt=login` act on the single sign-on (SSO) session that the application's sign-in flow keeps. See [`prompt` Values](../protocols/oauth-oidc/openid-connect.mdx#prompt-values).

### Add the Self-Service Permissions After an Upgrade

A deployment set up on an earlier release has no `self` resources on its System resource server. Until you add them, access tokens cannot carry the self-service permissions, so a change in the table above is refused with `403` when the token lacks the permission. A user whose role holds `system` passes the permission check, and with no action to carry a `maxAge`, the change needs no recent sign-in. To add them, import the System resource server document from `bootstrap/01-default-resources.yaml` with an upsert, as described in [Add System Permissions After an Upgrade](./manage-roles.mdx#add-system-permissions-after-an-upgrade). The imported actions carry `maxAge: 300`.

## Delete a User

1. Open the user from the **Users** list.
2. Click **Delete** and confirm.

:::warning
Deleting a user is permanent. The user's account, attributes, and group memberships are removed immediately.
:::

## Mandate Roles on a Shared User

A user can be [shared](../../key-concepts/resource-sharing.mdx) with the organization units beneath the one that owns it. A share can also mandate roles: for a child organization unit that the share names, it assigns the user the roles you list, in that organization unit.

A roles rule is accepted in one place only. It must sit on a unit listed under `childUnits` in `selected` mode, with `reach: unit`. A roles rule on `childUnits` in `all` mode, on `allUnits`, or on a unit with `reach: subtree` is refused with `USR-1039`.

```bash
curl -X POST https://localhost:8090/users/{userId}/sharing-policies \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "childUnits": {
      "mode": "selected",
      "units": [
        {
          "ouId": "acme-customer-a",
          "reach": "unit",
          "overlayRules": {
            "roles": {
              "editable": false,
              "value": ["<roleId>"]
            }
          }
        }
      ]
    }
  }'
```

The rule must set `editable` to `false` and list at least one role ID in `value`. Other shapes are refused:

| Rule | Error |
|---|---|
| `editable: true`, or `allowedValues` | `USR-1029`, because the rule would widen what the issuing organization unit holds. |
| No `value`, an empty `value`, or `excludedValues` | `USR-1040` |
| Roles on a server whose roles load only from resource files | `ROL-1038` |

Each role must also meet these requirements:

- The role is owned by, or shared with, the receiving organization unit. Otherwise the request fails with `ROL-1035`. <ProductName /> never shares the role for you.
- You hold every permission the role grants, the same rule as for adding a role assignment. Otherwise the request fails with `403 Forbidden` and the code `SAZ-4030`. See [Permission Requirements](./manage-roles.mdx#permission-requirements).

Mandating roles needs only the permission to manage users (`system:user`), not the permission to manage roles. An administrator who can share a user can therefore assign that user roles in the child organization units the share names, limited to roles that grant nothing the administrator lacks.

### How a Mandate Behaves

- Writing the share creates the mandated assignments in that organization unit. Updating the share brings them in line with the new list of roles, and deleting the share removes them.
- The child organization unit cannot remove a mandated assignment. It can still assign the same role to the same user directly, and it can remove that direct assignment. It can also add its own roles for the user.
- A role assignment response carries `isReadOnly: true` when the share mandates the assignment, and `isReadOnly: false` for a direct assignment.
- A share that the child organization unit makes onward can carry only roles from its own mandate.
- `GET /users/{id}/overlay-rules?ouId=<ouId>` returns the `roles` rule that applies to the asking organization unit.
- A role export leaves mandated assignments out, because they follow the share and would import back as direct assignments.

:::note
Removing a mandate does not revoke tokens that are already issued. The roles disappear from newly issued tokens. Removing a direct assignment through the REST API, by contrast, revokes the tokens that carry the role's permissions. See [Token Revocation](../protocols/oauth-oidc/token-revocation.mdx#role-assignment-removal).
:::

To import a user whose shares carry roles, put the user, the role, and the share in one import document. <ProductName /> replays the shares after the roles, so the document round-trips. See [Import Resources](../declarative-configurations/import-resources.mdx).

## Scope Users to a Project

On the control plane, a user can belong to a project. A user without a `projectId` belongs to the organization, so the users that exist today stay organization-level.

When a project is selected in the Console, **Users** lists only that project's users, and **Add user** creates the user in the project. When the project has organization units, it asks which one the user belongs to, offering only the ones the user type allows, with the first of them selected. A user type that can't be used in the project is reported before the user is created. With no project selected, **Administrators** lists every user, including the users of each project.

- **Create or update**: set `projectId` in the request body of `POST /users` or `PUT /users/{id}`. On create, a user in a project without `ouId` is placed in the system organization unit. An update names the user's organization unit in `ouId`. With `ouId`, it must be the system organization unit or an organization unit of the project. Any other organization unit fails the request with `USR-1043`, and a project that does not exist fails it with `USR-1042`. The organization unit must also be the user type's organization unit or one beneath it, so even the system organization unit fails for a user type owned by another organization unit. This check can fail first, with `USR-1023`.
- **Update without `projectId`**: the user keeps its current project. A different `projectId` moves the user to that project, unless the user is shared with other organization units, which fails the request with `USR-1038`. A user in a project stays in a project: no update returns it to the organization, so delete the user and create it again without a `projectId` to make it an organization user.
- **List**: `GET /users?projectId=<project-id>` returns the users of the project. To list only the ones an organization unit in the project owns, add `filter=ouId eq "<ou-id>"`. A project that does not exist returns an empty list.

A project groups users for management only. Sign-in, credentials, sharing, and role assignments work the same whatever project a user belongs to.
