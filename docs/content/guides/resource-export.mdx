# Export Resources

Use the export API to retrieve <ProductName /> resources:

- `POST /export`: returns a JSON object.

## JSON Response Shape

`POST /export` returns this payload:

```json
{
  "resources": "# File: My_App.yaml\napiVersion: thunder/v1\n...",
  "environment_variables": "APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_ID=\nAPPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_SECRET=\n"
}
```

Field behavior:

- `resources`: Combined YAML output for all exported resources, with `# File:` headers and `---` separators.
- `environment_variables`: environment file content with one assignment per detected template variable. A
  variable is left empty, except one for a list the resource does not have, such as an application's
  `redirectUris` when it has none, which is written as `[]` so the file imports as it is.

If the export has no template variables, `environment_variables` is an empty string.

Organization units come out in the same order every time: each unit before the units under it, units
under the same parent by name, and each unit once however it is reached. Exporting units that have not
changed therefore gives the same text.

## Template Variable Names

Each parameterized field becomes a template variable named after the resource type, the resource ID
and the field, in uppercase, joined by double underscores. The `clientId` field of an application whose
ID is `0198f3a1-7c2e-7b10-9a44-5d3e8f21c6b7` becomes `APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_ID`.

Each part has a job:

- The resource type leads the name because an ID is only unique within its own type. An application
  and an agent could otherwise claim the same variable.
- The resource ID is what makes the name belong to one resource. A name is not unique once it is
  normalized: `alice@example.com` and `alice.example.com` read the same, and so would the passwords
  they hold. Their IDs never do. The ID is written in full, because a shortened one could be matched
  on purpose by someone who chooses the ID of a resource they import.
- The field is the field the value belongs to, such as `CLIENT_ID` or `PASSWORD`.

The name of the resource is not part of the variable. A name can change and can repeat, so a variable
built from it could stop agreeing with the value held for it, or be shared by two resources. The ID does
neither. Look up a resource's ID to find its variables, or read them from the export, which writes each
one next to the field it stands for.

The resource ID is written without hyphens in uppercase when it is a lowercase UUID, which is what
<ProductName /> generates. Any other ID, such as one a declarative file names, is hashed and written
as `H` followed by 32 hexadecimal digits, so `my-app` and `my_app` never share a name.

No part can contain a double underscore, so a name always reads back as exactly one resource type, ID
and field.

Exported file names and resource attribute values keep their original text.

For an agent, export uses the label resolved from the agent type's `systemAttributes.display` setting for the file name. The default mapping reads `attributes.name`; if no display value is available, export uses the agent ID. The YAML stores the name under `attributes.name`, not in a top-level `name` or `display` field. See the [agent resource example](../declarative-configurations/import-resources#agent-resources).

| Resource type | Resource ID | Variable name for `clientId` |
| --- | --- | --- |
| `application` | `0198f3a1-7c2e-7b10-9a44-5d3e8f21c6b7` | `APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_ID` |
| `agent` | `0198f3a1-7c2e-7b10-9a44-5d3e8f21c6b7` | `AGENT__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_ID` |
| `application` | `my-app` | `APPLICATION__H<32 hexadecimal digits>__CLIENT_ID` |

Two resources never share an ID, so two applications named `Wayfinder-Concierge` and
`Wayfinder_Concierge` still get different variables and each keeps its own value in the environment file.

### Updating an Existing Environment File

Variable names generated from the resource type and name carry no ID. An environment file kept from
an earlier export sets names such as `APPLICATION_MY_APP_CLIENT_ID`, which a current export no longer
asks for. Rename each entry to the new name, or export again and fill in the new
file. A field that already holds a reference keeps the name it was stored with, as described in
[Stored References Keep Their Names](#stored-references-keep-their-names).

## User Credentials

Every user is exported, whether or not it has a password. A user who has one carries it as a
template variable rather than a value:

```yaml
credentials:
  password: "{{.USER__0198F3A17C2E7B109A445D3E8F21C6B7__PASSWORD}}"
```

A stored password is a one-way hash, so the original cannot be exported. Naming it here means the
importing server supplies the password from its own environment or secret provider and hashes it on
the way in, which leaves the imported user able to sign in. Without the placeholder the user would
import with no credential at all.

Which credentials a user carries depends on its user type. The export includes each credential the
user type declares, such as `password`, when the user has set it. A credential the user has not set
is left out, so a user created without a password exports with no `credentials` block, and the
import asks for nothing it would never use. A credential outside the user type, such as a passkey,
is never exported: it is bound to a device and means nothing on another deployment.

A user with no username is not exported at all, so it carries no credentials either.

The password variable is named after the user's ID. Two users whose usernames normalize to the same
text, such as `alice@example.com` and `alice.example.com`, therefore get different password variables
and import with their own passwords.

<ProductName /> still refuses the whole export with the error `EXP-1003`, naming the two resources,
if two resources ever claim one variable. The bundle is not returned at all, because one that dropped
a resource silently would look complete.

## Agent Credentials

An agent carries its credentials the same way a user does. An agent named `Support Bot` that has a
password exports:

```yaml
credentials:
  password: "{{.AGENT__0198F3A17C2E7B109A445D3E8F21C6B7__PASSWORD}}"
```

The export includes each credential the agent type declares, such as `password`, when the agent has
set it, and leaves out a credential the agent has not set. The variable is named after the agent's ID. The agent's OAuth client secret is not one of these credentials: it stays under
`inboundAuthConfig` and is parameterized like any other field.

Agent display names do not have to be unique. Two agents with the same display name get different
password variables because each is named after its own ID.

The import sets the credentials after it writes the agent. It refuses a credential the agent type
does not declare, one that is not a string, and one with no value. A new agent refused that way is
deleted again, so a retry does not meet half of it. An agent that already exists keeps the profile
the import wrote, and the import reports that its credentials were not updated.

A declarative agent file takes the same `credentials` block, so a data-plane export of an agent
loads as a file as it is. The file is loaded as written, without checking its credentials against
the agent type, but it cannot set a credential the system manages, such as `clientSecret`,
`flowSecret`, or `passkey`. A control-plane export does not load as a file: its credentials are
`sec:` references, which only an import resolves.

## Resource Server Identifiers

A resource server's `identifier` is the audience it is served under, such as an API's base URL or
an MCP server's URL, and each deployment usually serves it under its own. The identifier is exported
as a template variable named like any other field, so a resource server exports:

```yaml
identifier: {{.RESOURCE_SERVER__0198F3A17C2E7B109A445D3E8F21C6B7__IDENTIFIER}}
```

Its resources, actions, and delimiter are exported as they are.

## Exports From a Control Plane

What an export contains depends on the plane you export from. A data plane holds its own values, so
each parameterized field carries a template placeholder, and `environment_variables` lists the
placeholders for you to fill in. A control plane authors configuration but does not hold the values
it refers to. Each parameterized field carries a reference instead, naming where a data plane holds
the value, and there is nothing to fill in.

The same application exported from each plane:

```yaml
# From a data plane
oauth:
  clientId: {{.APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_ID}}
  clientSecret: {{.APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_SECRET}}

# From a control plane
oauth:
  clientId: var:APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_ID
  clientSecret: sec:APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_SECRET
```

A reference names one of two collections:

| Prefix | Refers to | Example |
| --- | --- | --- |
| `var:` | An ordinary value, such as a client ID | `var:APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_ID` |
| `sec:` | A credential, such as a client secret | `sec:APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_SECRET` |

A list, such as an application's redirect URIs, exports as a list holding one `var:` reference. The
variable it names holds the items, as described in [Value References](./declarative-configurations/value-references.mdx#a-list-of-values).
An empty list exports as it is, with no reference.

The prefix is what keeps a credential out of a read. A data plane returns a variable's value when
asked for it, and never returns a secret's. A client secret, a connection's secret or token, and any
property marked `isSecret` always export with `sec:`.

### Stored References Keep Their Names

A field that already holds a reference exports as it stands. The name in a reference records where
the value went, so renaming the resource does not change it. An application renamed from `Old Name`
to `New Name` still exports `sec:APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_SECRET`, because that is the name the
data plane holds the secret under.

Each entry in a list gets the same treatment on its own. In an application with two inbound
configurations, a reference already placed in one is kept, and a value in the other is replaced
with a new reference.

### What a Control Plane Does Not Parameterize

A control-plane export writes no template placeholders, the credentials of users and agents
included. Those are written as `sec:` references named as their template variables are, such as
`sec:USER__0198F3A17C2E7B109A445D3E8F21C6B7__PASSWORD`. See [User Credentials](#user-credentials) and
[Agent Credentials](#agent-credentials). Every control-plane export therefore leaves
`environment_variables` empty.

### A Credential That Refers to a Variable

<ProductName /> refuses to export a credential that refers to an ordinary variable, such as a client
secret holding `var:APPLICATION__0198F3A17C2E7B109A445D3E8F21C6B7__CLIENT_SECRET`. Exporting it as it stands would point the
credential at a value a read returns. Changing the prefix to `sec:` would name a secret that was
never stored.

The export leaves that resource out and logs a warning naming it. The other resources export as
usual. Update the field to a `sec:` reference that names the stored secret, then export again.

## Internal API Model Reference

The API reference schema also defines an internal `ExportResponse` model (see `ExportResponse.envFile`, backed by the `EnvironmentFile` schema/struct):

```json
{
  "files": [
    {
      "fileName": "google-idp.yaml",
      "content": "resource_type: connection\ntype: google\n...",
      "size": 128
    }
  ],
  "envFile": {
    "fileName": ".env",
    "content": "CONNECTION_GOOGLE_CLIENT_ID=\nCONNECTION_GOOGLE_CLIENT_SECRET=\n",
    "size": 62
  },
  "summary": {
    "totalFiles": 2,
    "totalSizeBytes": 190
  }
}
```

When no template variables are detected, `envFile` is omitted (or `null` in internal JSON serialization paths).

## Format Option

In `options.format`, only `yaml` is currently supported for generated resource content.
