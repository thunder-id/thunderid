# Build a Multi-Factor Sign-In Flow

By the end of this guide, you will have a sign-in flow that offers two first-factor options: username + password, or Google social login. Users who choose username + password are prompted for a second factor via SMS OTP. Users who sign in with Google skip the second factor and go straight to login success.

## Flow Structure

The two paths diverge at the login screen and both end at login success, the password path with an extra OTP step.

<BuildAFlowDiagram />

## Prerequisites

- <ProductName /> is running. See [Get Started](../../../getting-started/get-thunderid).
- You have created an application. See [Register an Application](../../applications/manage-applications).
- A Google identity provider is configured in <ProductName />. See [Add Google](../../identity-providers/add-google).
- An SMS notification sender is configured. See [SMS Sender](../../notifications/sms-providers).
- Each user's profile in <ProductName /> includes a mobile number. The SMS OTP executor reads the number from the user store.

<Stepper>

## Create the Flow

1. Sign in to the <ProductName /> Console at [https://localhost:8090/console](https://localhost:8090/console).
2. Go to **Flows** and click **+ Create New Flow**.
3. If your deployment has more than one organization unit, the Console asks which organization unit the flow belongs to. Select the organization unit that owns the flow, then click **Continue**. You cannot change it later. With exactly one organization unit, the Console uses it and skips this step.
4. Select **Sign-in** as the flow type and click **Continue**.
5. Select **+ Start from scratch** and enter a flow name, for example `MFA Sign In`.
6. Click **Create**.

The canvas opens with a **START** node, a blank **View** node, a **Auth Assertion Generator**, and an **END** node.


## Add the Username + Password Option

1. Delete **Blank View**.
2. From **Steps**, click **+** next to **Username + Password**. This replaces the default blank View with the login form View node.
3. From **Executors**, click **+** next to **Identifier + Password**.
4. On the **Username + Password** View node, click the **Sign In** button component and set its **Action** property to **Submit form**.
5. Connect **START** → **Username + Password View** → **Identifier + Password Executor**.

## Add the Google Social Login Option

From the left panel under **Widgets**, click **+** next to **Continue with Google**.

This adds three elements to the canvas:
   - A **Continue with Google** button action on the **Username + Password** View node
   - A **Google** Executor node
   - An **Auth Assertion Generator** Executor node (pre-wired to **END**)

The login screen now has two actions: the **Sign In** button (routes to the Identifier + Password executor) and the **Continue with Google** button (routes to the Google executor).

## Add SMS OTP as the Second Factor

After a successful username + password check, the flow sends a one-time password (OTP) to the user's registered mobile number and asks them to verify it. This second factor is built from four nodes:

| Node | Role |
|---|---|
| **Generate OTP** Executor | Generates the OTP and stores it for delivery. Runs in the background, no user interaction. |
| **Send SMS** Executor | Delivers the generated OTP to the user's mobile number via SMS. Runs in the background, no user interaction. |
| **SMS OTP View** | Presents the OTP entry screen to the user. |
| **Verify OTP** Executor | Validates the code the user entered. |

## Add the OTP View and Verify OTP Executor

1. From **Steps**, click **+** next to **SMS OTP View**. Click the **Verify** button component and set its **Action** property to **Submit form**.
2. From **Executors**, click **+** next to **Verify OTP**.
3. Connect **Send SMS** success → **SMS OTP View**.
4. Connect **SMS OTP View** action output → **Verify OTP** Executor.

## Configure the Verify OTP Executor

1. Connect the **Verify OTP** Executor's **incomplete** output back to the **SMS OTP View** node so users can retry an incorrect code.
2. Connect the **Verify OTP** Executor's **success** output to the **Auth Assertion Generator** Executor's input.

## Verify the Wiring

Before saving, confirm these connections:

| From | Port | To |
|---|---|---|
| **START** | - | **Username + Password View** |
| **Username + Password View** (Sign In) | action | **Identifier + Password** Executor |
| **Username + Password View** (Continue with Google) | action | **Google** Executor |
| **Identifier + Password** | success | **Generate OTP** Executor |
| **Identifier + Password** | incomplete | **Username + Password View** |
| **Google** | success | **Auth Assertion Generator** Executor |
| **Generate OTP** | success | **Send SMS** Executor |
| **Send SMS** | success | **SMS OTP View** |
| **SMS OTP View** (Verify) | action | **Verify OTP** Executor |
| **Verify OTP** | success | **Auth Assertion Generator** Executor |
| **Verify OTP** | incomplete | **SMS OTP View** |
| **Verify OTP** | failure | *(unconnected, flow terminates; wire to error View in production)* |
| **Auth Assertion Generator** | success | **END** |

:::note
Every executor has a failure output (red dot). An unconnected failure output causes the flow to terminate with an unhandled error and no feedback to the user. This guide leaves failure outputs unconnected for simplicity. See [Always Wire Failure Outputs](./#always-wire-failure-outputs).
:::

## Save the Flow

Click **Save** in the top-right corner. <ProductName /> saves the flow and assigns it a version.

## Assign the Flow to Your Application

A flow has no effect until it is assigned to an application.

1. In the Console, go to **Applications** and open the application you created.
2. Open the **Flows** tab.
3. Under **Authentication Flow**, select the flow you just saved from the dropdown.
4. Click **Save**.

<ProductName /> now runs this flow for every sign-in to your application. Password-based users are challenged with an SMS OTP; Google users complete sign-in in a single step.

<details>
  <summary>Build flows for an application that serves many organizations</summary>

  When each customer of your application is an organization unit beneath one parent OU, three templates cover sign-up and sign-in:

  - **Organization Sign-up** (Self sign-up): a new customer creates their account and their organization in a single sign-up. The flow asks for the account details first, then for the organization's name and, optionally, a handle, which is made from the name when left empty. It creates the organization beneath the user type's OU, creates the user inside that organization, and assigns the roles you set on the **Assign Roles** step. The user belongs only to the organization they created.
  - **Organization Sign-up with Shared Account** (Self sign-up): the same sign-up, but the account stays outside the organization. The flow creates the user in the user type's OU, affiliates the user with the new organization on its **Share** step, and then assigns the roles there. Because the account is not tied to one organization, it can be affiliated with more organizations later. A user can be shared only into a direct child of the OU that owns them, so this template always creates the organization directly beneath the user type's OU.
  - **Basic + Enterprise SSO** (Sign in): a password sign-in, or **Sign in with SSO**, which asks for the organization's handle and signs in through the OpenID Connect connection that organization chose. A first-time SSO user is created in the organization.

  These templates name values only your deployment has:

  - The sign-up templates open unsaved, and **Save** stays disabled until you set the role IDs on the **Assign Roles** step.
  - The sign-in template is saved when you create it. Both **Resolve OU** steps start with the OU the flow belongs to as their parent OU: the OU you choose when you create the flow, or the system organization unit for a flow in a project that has no OUs of its own. If your organizations sit beneath another OU, change the parent OU on both steps.

  To make them work across your organizations:

  - Share the roles from the parent OU with all of its child OUs, with their assignments editable, so a role can be assigned in an organization the sign-up just created. See [Share a Role With Other Organization Units](../users/manage-roles.mdx#share-a-role-with-other-organization-units).
  - Share the sign-in flow with the child OUs and make its `enterpriseIdp` variable editable, so each organization sets its own connection. See [Share a Flow](./share-a-flow.mdx).
  - Share the application with the child OUs, so a sign-in can land in any of them.

</details>

<details>
  <summary>Build and configure a user onboarding flow</summary>

  A user onboarding flow controls how administrators create and onboard new users. Unlike authentication, registration, and recovery flows, which are assigned per application, the user onboarding flow is configured **system-wide**. It runs whenever an admin creates a user through the <ProductName /> Console, regardless of which application they are working in. The same flow also governs admin-initiated user creation via the API.

  The default built-in flow walks the admin through the following steps:

  1. **Permission check**: validates that the caller holds `system:user:create`. The flow runs as the admin, so creating the user also needs that permission in the target OU. See [Permissions for Administration Flows](../../users/manage-roles#permissions-for-administration-flows).
  2. **User type selection**: if multiple user types are configured, prompts the admin to select one.
  3. **Organization unit (OU) selection**: prompts the admin to choose the target OU from the OU tree.
  4. **Onboarding mode**: the admin chooses between two paths:
     - **Create now**: the admin fills in the user's profile details immediately and the user is provisioned on the spot.
     - **Invite**: the admin enters the user's email address and selects a delivery method: send an invitation email, or copy a shareable link. The invited user follows the link to complete their own registration (the invite link is valid for 24 hours).

  To customize the user onboarding flow, you can either edit the default flow directly in the Console's Flow Builder, or create a new one via the `/flows` API, which requires the `ouId` of the organization unit that owns the flow. See [Organization Unit Ownership](../flow-concepts#organization-unit-ownership) and the [API Reference](../../../apis).

  To set the flow as the active system-wide user onboarding flow, call the Server Configuration API. A `PUT` replaces the section's runtime layer, including the default handles for the other flow types, so read the section first, change only `userOnboardingFlow` with `jq`, and send the full value back:

  ```bash
  curl -fksL https://localhost:8090/server-config/flow \
    -H "Authorization: Bearer $TOKEN" \
    | jq '.writable | .userOnboardingFlow.defaultHandle = "<your-flow-handle>"' > flow.json

  curl -kL -X PUT https://localhost:8090/server-config/flow \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d @flow.json
  ```

</details>

## Build an agent onboarding flow

Agent onboarding uses an **Administration** flow in the signed-in administrator's Console session. It is separate from the authentication flow that an agent's users run later. The direct Agent API does not run the onboarding flow.

The builder provides one **Provisioning** step for users and agents. The preceding type resolver supplies the category and schema. For agents, keep the **Agent Type** step before the uniqueness check and **Provisioning**.

1. In **Flows**, click **+ Create New Flow**. Select **Administration**.
2. Select **Agent Onboarding Flow (Own Identity)**, **Agent Onboarding Flow (On Behalf of a User)**, or **Agent Onboarding Flow (Choose Mode)**.
3. Enter a name and create the flow.
4. Review the shared steps below. Configure **Delegated mode** on **Provisioning** for the intended agent behavior.
5. Save the flow. Set its handle as the [agent onboarding default](../../agents/manage-agents#make-the-flow-active).

| Step | Configuration |
|---|---|
| Validate Permission | Keep the administrator permission check before onboarding. |
| Agent Type | Set `allowedAgentTypes` to `["default"]` for the built-in agent type. The resolver supplies `categoryName: agent` and `categoryType` for uniqueness validation and provisioning. |
| Resolve OU | Resolve the target organization unit after the agent type. |
| Owner | Offer a user selection. The Console preselects the signed-in administrator, and a submission without an owner also resolves to the authenticated caller. |
| Agent Details | Collect schema attributes, including `name`. Add fields for custom attributes or use a dynamic input prompt on Provisioning's incomplete path. To collect the agent's lifespan, add a **Date Time Input** bound to `validUntil`. See [Set a lifespan during onboarding](../../agents/agent-lifespan#set-a-lifespan-during-onboarding). |
| Validate Attribute Uniqueness | Use the category and type supplied by the **Agent Type** step. Route incomplete results back to **Agent Details**. |
| Delegation settings | Add **Delegated Agent Details** to collect `redirectUris`, `authFlowId`, and `allowedUserTypes`, or **Choose Agent Mode** to collect these fields and `delegated`. Connect the widget after a successful uniqueness check and before Provisioning. |
| Provisioning | Set `includeOptional: true`. Enable **Delegated mode** (`delegated: true`) for an OBO-only flow. With **Choose Agent Mode**, the collected `delegated` value overrides the node's fallback. |
| Credential display | Present `agentId`, `clientId`, and `clientSecret` from the provisioning response. |

The supplied templates connect Provisioning's failure output to **Agent Details**. The own-identity template also sends incomplete results there; the OBO and Choose Mode templates use a dynamic input prompt for missing inputs. Keep these return paths when customizing the flow. Flow execution does not provide a general rollback of an agent after provisioning succeeds.

To assign access during onboarding, select existing groups in **Assign group** (`assignGroup`) and existing roles in **Assign role** (`assignRole`) on Provisioning. The executor assigns them after creating the agent. See [Assign groups and roles during onboarding](../../agents/manage-agents#assign-groups-and-roles-during-onboarding).

Both parts are needed for OBO: the flow collects the delegation settings, and provisioning receives `delegated: true` from its property or the administrator's selection. The **Login flow** field saves an existing authentication flow on the agent; it does not add user sign-in or consent steps to the onboarding flow. See [Configure onboarding for agents that act on behalf of users](../../agents/manage-agents#configure-onboarding-for-agents-that-act-on-behalf-of-users) for the widget setup.

For properties, input types, and node examples, see [Advanced Configurations](../advanced-configurations#user-provisioning-and-attributes). For administrator creation steps, see [Create and Manage Agents](../../agents/manage-agents).

<details>
  <summary>Build and configure an invitation flow</summary>

  An `INVITATION` flow lets an organization unit admin invite a user into their unit. Start it by flow ID on `POST /flow/execute` with an access token that carries a `system` permission and is issued for an organization unit. It cannot be started by `flowType`. The flow acts for the OU in the token's `ouId`, and an `ouId` sent as an input does not change it. A token without an `ouId` is refused with `403` and the code `FES-1027`. That OU must own the flow or have it shared with it, through `POST /flows/{flowId}/sharing-policies` on the owning OU. A flow shared with neither is refused with `403` and the code `FES-1029`.

  The template starts with a **Permission Validator** step requiring `system`. The roles an admin may grant and the share are checked against the permissions the admin holds. An invitation flow is bound to one user type, which its **User Type Resolver** step names in `allowedUserTypes`. The step fails with `FET-1135` unless it names exactly one type. The template's **Provisioning** step sets `provisioningOU` to `userType`, so new users are created in the OU that owns that type.

  The flow runs in two parts on one execution. The admin's part identifies the user by email, authorizes the share, selects roles, and sends the invite. Send every step of it with the admin's access token: the Validate Share and Select Roles steps refuse any other caller. The invitee's part continues the same execution through the invite link and needs no token. It runs with the server's authority. On acceptance, the flow shares the user into the admin's OU and assigns the roles as the admin, with the permissions the admin still holds then, creating the user first on the new-user branch. If the admin holds none of them by then, the user is shared in without the roles. Declining writes nothing. In the flow designer, start from the **Invite into Organization** template and name the user type on its **User Type Resolver** step. The admin can skip the email and role prompts by sending `email` and `roles` (role IDs separated by spaces) as inputs with the action `action_submit_email` on the request that starts the flow. The roles are checked as they are on the prompt, and an email that names no account still stops once at the **No Account Found** confirmation. Its invitations use the `invitation` email template, which asks the user to accept or decline joining the organization, and its **Send Email** steps need a sender (`senderId`).

  The template branches on the **Identifying** executor in `identify` mode, with `boundToUserType` and `continueOnNoMatch` set. A user of the flow's type follows `onSuccess` (the existing-user branch). No match follows `onIncomplete` (the new-user branch) without an error, so the email is kept for the invite and the account. A user of another type fails with `FET-1054`, and several matches fail with the ambiguous identity error, both on `onFailure`, so the admin can enter another email.

</details>

  <summary>Build and configure a sign-out flow</summary>

  A sign-out flow terminates the [Single Sign-On session](../../../key-concepts/authentication/sessions) an authentication flow established, so a user is fully signed out rather than silently signed in again on their next visit. The default flow ends the session without prompting, and a custom flow can confirm the sign-out with the user first. Every application already resolves to a flow, the one it pins, its organization unit's default, or the server-level default, so you only build a sign-out flow when you want to change that behavior. To create one:

  1. In the Console, go to **Flows** → **+ Create New Flow**.
  2. If your deployment has more than one organization unit, select the organization unit that owns the flow and click **Continue**. You cannot change it later. With exactly one organization unit, the Console skips this step.
  3. Select **Sign Out** as the flow type and click **Continue**.
  4. Choose a template, for example, **Silent Sign Out** ("Terminate the user's SSO session immediately, with no confirmation step"), **Confirm & Sign Out** (prompt on every request), **Conditional Confirmation** (prompt only when the request has no `id_token_hint`), or **Blank** to start from scratch.
  5. Give the flow a name and click **Create**.
  6. The canvas opens with the template pre-wired. The **End Session** executor is the node that terminates the session. Customize the steps as needed, then click **Save**.

  To use your flow instead of the default on an application:

  1. Go to **Applications** and open the application.
  2. Open the **Flows** tab and find the **Sign out flow** section.
  3. Select the flow you created from the dropdown.
  4. Click **Save**.

  To make it the default for every application in an organization unit instead, go to **Organization units** and open the organization unit. Open the **Flows** tab, select the flow under **Sign out flow**, then click **Save**. An application that pins its own flow keeps using that flow.

  The sign-out flow runs when a user signs out of the application. Browser-based applications trigger it over OIDC through the [RP-Initiated Logout](../../protocols/oauth-oidc/rp-initiated-logout) endpoint; app-native applications run it directly through the Flow Execution API by initiating a `SIGNOUT` flow. See [API Reference](../../../apis).

<details>
  <summary>Build a self attribute verification flow</summary>

  A **Self** flow runs an operation that a signed-in user performs on their own account. It is never assigned to an application. Your application starts it through the Flow Execution API with `flowType` set to `SELF`, the flow's `handle`, and the user's access token. <ProductName /> binds the user of that token to the execution, so a later request continues the flow with its `executionId` and `challengeToken` alone. See [API Reference](../../../apis).

  <ProductName /> ships `default-self-attribute-verification-flow`, which records that the user controls their email address or mobile number. Start it with the attribute to verify:

  ```bash
  curl -kL -X POST https://localhost:8090/flow/execute \
    -H "Authorization: Bearer $USER_ACCESS_TOKEN" \
    -H "Content-Type: application/json" \
    -d '{ "flowType": "SELF", "handle": "default-self-attribute-verification-flow", "inputs": { "attribute": "email" }, "verbose": true }'
  ```

  The flow prepares the attribute, sends a one-time code to the stored email address or mobile number, checks the code, and records the verification.

  Build a flow of your own, for example one that sends a link instead of an email code:

  1. In the Console, go to **Flows** → **+ Create New Flow**.
  2. If your deployment has more than one organization unit, select the organization unit that owns the flow and click **Continue**. You cannot change it later. With exactly one organization unit, the Console skips this step.
  3. Select **Self** as the flow type and click **Continue**.
  4. Choose a template: **Self Attribute Verification** (a one-time code for an email address or mobile number), **Self Attribute Verification with Email Link** (a link for an email address, a one-time code for a mobile number), or **Blank** to start from scratch.
  5. Give the flow a name and click **Create**.
  6. The canvas opens with the template pre-wired. Select the senders as described below, customize the steps as needed, then click **Save**.

  The **Send Email** node sends only through the email provider that it names, and the **Send SMS** node only through the SMS sender that it names. In `default-self-attribute-verification-flow`, the **Send Email** node ships without an email provider and the **Send SMS** node with the `{{SENDER_ID}}` placeholder, so neither node sends anything until you select your email provider and your SMS sender on those nodes. To select them in the Console:

  1. Go to **Flows** and open the flow, for example **Default Self Attribute Verification Flow**.
  2. Click the configure icon on the **Send Email** node and select your provider in **Email provider**.
  3. Click the configure icon on the **Send SMS** node and select your sender in **Notification sender**.
  4. Click **Save**.

  When the Console opens a flow, it fills an empty **Email provider** with your first email provider, and an empty **Notification sender** when you have exactly one SMS sender. The flow sends through them only after you save it. See [Configure an Email Provider](../../notifications/email-providers) and [Configure an SMS Provider](../../notifications/sms-providers). The one-time codes use the `otp` email and SMS templates, and the email link sends `self-email-verification`. See [Default Templates](../../declarative-configurations/import-resources#default-templates).

  For how long a `SELF` flow stays open, see [Flow Defaults](../../../deployment/configuration#flow-defaults).

</details>

<details>
  <summary>Build an administrator attribute verification flow</summary>

  An administrator-initiated flow is started by an administrator for a user and finished by that user. It is never assigned to an application. An administrator starts it through the Flow Execution API with `flowType` set to `ADMIN_INITIATED`, the flow's `handle`, the user's ID as the `subject` input, and an access token carrying a `system` permission. The flow must be owned by, or shared with, the organization unit the token is issued for. The shipped flow's **Validate Permission** step then requires `system:user:update` or `org:user:update`, and the flow needs permission to update that user. The flow runs as that administrator, so an organization unit administrator can send a link only to users of its own organization units: the user continues it from the link it sends, with no access token, and those steps run with the permissions the administrator still holds, so the link stops working once the administrator loses them. See [Permissions for Administration Flows](../../users/manage-roles#permissions-for-administration-flows) and [API Reference](../../../apis).

  <ProductName /> ships `default-admin-attribute-verification-flow`, which emails the user a link to verify their email address. Start it with the user's ID:

  ```bash
  curl -kL -X POST https://localhost:8090/flow/execute \
    -H "Authorization: Bearer $ADMIN_ACCESS_TOKEN" \
    -H "Content-Type: application/json" \
    -d '{ "flowType": "ADMIN_INITIATED", "handle": "default-admin-attribute-verification-flow", "inputs": { "subject": "<user-id>" }, "verbose": true }'
  ```

  The flow prepares the user's stored email address, sends it the `admin-initiated-email-verification` email, and answers the administrator that the link was sent. The administrator never receives the link, even when the email cannot be sent. The user opens the link, confirms, and the flow records the verification. The start binds the flow to the user it names, so no later request can change that user. The flow verifies `email` unless the start names another email attribute in the `attribute` input, such as `"attribute": "workEmail"`. It sends the link by email, so name only an email attribute.

  Build a flow of your own:

  1. In the Console, go to **Flows** → **+ Create New Flow**.
  2. If your deployment has more than one organization unit, select the organization unit that owns the flow and click **Continue**. You cannot change it later. With exactly one organization unit, the Console skips this step.
  3. Select **Administrator-initiated** as the flow type and click **Continue**.
  4. Choose the **Administrator Attribute Verification with Email Link** template.
  5. Give the flow a name and click **Create**.
  6. The canvas opens with the template pre-wired. Select the email provider as described below, customize the steps as needed, then click **Save**.

  The **Send Email** node sends only through the email provider that it names. In `default-admin-attribute-verification-flow`, the **Send Email** node ships without an email provider, so the flow sends nothing until you select your email provider on that node. To select it in the Console:

  1. Go to **Flows** and open the flow, for example **Default Admin Attribute Verification Flow**.
  2. Click the configure icon on the **Send Email** node and select your provider in **Email provider**.
  3. Click **Save**.

  When the Console opens a flow, it fills an empty **Email provider** with your first email provider. The flow sends through it only after you save it. See [Configure an Email Provider](../../notifications/email-providers). The link email uses the `admin-initiated-email-verification` template. See [Default Templates](../../declarative-configurations/import-resources#default-templates).

## Development Tips

### Always Wire Failure Outputs

Every executor has a failure output (red dot). Leaving it unconnected does not mean the flow ignores failures: it means the flow terminates with an unhandled error and the user sees nothing. Connect every failure output to either:

- An **error View** that displays a descriptive message
- The **END** node to terminate the flow explicitly

For retry behavior, such as letting a user re-enter an incorrect OTP, use the **incomplete** output, not the failure output. Wire the incomplete output back to the input View.

### Pass the `user` Object Between Executors

Most executors read from and write to the `user` context variable. The typical chain is:

```text
Identify User → sets user
  ↓
Identifier + Password → confirms user is authenticated
  ↓
Authorization → enriches with granted scopes
  ↓
Auth Assertion Generator → issues token for user
```

Ensure executors earlier in the flow populate `user` before executors that depend on it.

### Use Attribute Collector for Progressive Profiling

The Attribute Collector's incomplete path lets you collect profile data gradually across multiple sign-ins rather than demanding everything at registration. Wire a View after the incomplete path, collect the missing attributes, and the next execution of Attribute Collector will not re-prompt for fields already provided.
