# Token Revocation

**Token Revocation** ([RFC 7009](https://datatracker.ietf.org/doc/html/rfc7009)) lets a client tell <ProductName /> that a token should stop working before it expires. <ProductName /> extends this with broader scopes, so an operational event such as a sign-out, a user deletion, an account suspension, an application deletion, a role deletion, a group deletion, or a role assignment removal can invalidate many tokens at once.

Access tokens are self-contained JWTs, so a resource server that validates them locally has no way to know a token was revoked. <ProductName /> solves this with a denylist that both the authorization server and resource servers consult. The scopes below differ only in what goes on that list.

## Revocation Scopes

| Scope | What it invalidates | Typical trigger |
|---|---|---|
| **Single token** | One token, by its `jti` | A client calls `/oauth2/revoke`; a refresh token is rotated |
| **Grant** | Every token of one authorization grant, by its `tfid` | Sign-out, refresh-token replay, authorization-code replay |
| **Subject** | Every token issued to one user, agent, or application, by its `sub` | A user is deleted; a user, agent, or application is suspended |
| **Client** | Every token issued through one OAuth client, by its client ID | An application, or an agent with an OAuth client, is suspended; an application is deleted or its client secret is replaced |
| **Subject and permission** | Every token issued to one user, agent, or application that carries one of the given permissions for its audience | A group whose roles grant those permissions is deleted, for each of its members |

A token is rejected if **any** of these matches.

## Revoke a Single Token

<details>
<summary>How <ProductName /> Implements It</summary>

| Aspect | Behavior |
|---|---|
| Endpoint | `POST /oauth2/revoke` |
| Authentication | Required, same client authentication method as the token endpoint (see [Client Authentication Methods](../client-authentication-methods)) |
| `token` parameter | Required. The access token or refresh token to revoke |
| `token_type_hint` parameter | Accepted but not used internally: the server determines the token type itself |
| Success response | HTTP 200 with an empty body, as RFC 7009 §2.2 requires |
| Unknown or already-expired token | HTTP 200. The endpoint never reveals whether a token existed |
| Token issued to another client | HTTP 400 with `invalid_grant` |
| Tokens supported | Access tokens and refresh tokens |
| Signature | Verified before anything is recorded, so a token <ProductName /> did not issue cannot be added to the denylist |
| Expired tokens | Still revocable. Expiry is ignored on this endpoint, so an expired token can be presented to revoke the rest of its grant |

</details>

```bash
curl -X POST https://{{productSlug}}.example.com/oauth2/revoke \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d "token=$ACCESS_TOKEN"
```

A successful revocation returns `200 OK` with no body.

### Ownership

RFC 7009 §2.1 requires the server to verify that the token was issued to the authenticated client. <ProductName /> enforces this for both token types: access tokens are matched on their `client_id` claim, and refresh tokens on their `sub` claim, which carries the owning client. A client attempting to revoke another client's token receives `invalid_grant`.

## Grant-Scoped Revocation

Revoking one token of a grant usually should not leave its siblings working. Five refreshes produce a chain of access and refresh tokens that all descend from the same authorization, and revoking the newest refresh token alone would leave live access tokens behind.

<ProductName /> groups these into a **token family**, identified by a `tfid` claim carried on every token of the grant. By default, revoking any token of a family revokes the family in both directions: revoking a refresh token invalidates the access tokens issued alongside it, and revoking an access token invalidates the refresh token that would mint replacements. [What Revokes a Family](#what-revokes-a-family) below lists the setting that controls this, along with the other triggers.

### Where `tfid` Comes From

| Flow | Behavior |
|---|---|
| Authorization code with SSO | Minted when the session is established and stored against the session participant, which is what makes sign-out revocation possible |
| Authorization code without SSO | Minted when the authorization code is created, so the grant is still revocable |
| Refresh | Copied to the new tokens, so a family survives rotation |
| Token exchange | Controlled by `oauth.token_exchange.token_family`. `none` (the default) issues an independent token; `inherit` copies the subject token's family |
| Client credentials, CIBA | No `tfid`. There is no user grant to group, so family-scoped revocation does not apply |

### What Revokes a Family

| Trigger | Setting | Default |
|---|---|---|
| A client revokes a token that carries a `tfid` | `oauth.revocation.token_family.on_explicit_revoke` | `true` |
| A rotated-out refresh token is presented again (replay) | `oauth.revocation.token_family.on_refresh_replay` | `true` |
| An authorization code is redeemed twice (replay) | `oauth.revocation.token_family.on_code_replay` | `true` |
| The user signs out through RP-Initiated Logout | Always on | Not configurable |

:::note
Refresh-token replay detection depends on rotation, since a token can only be replayed once it has been rotated out. Enable `oauth.refresh_token.renew_on_grant` to use it.
:::

Session **sign-out** revokes the family. Session **expiry** does not: a session that simply times out leaves its tokens valid until they expire on their own.

## Subject-Scoped Revocation

Some events invalidate tokens that no single client is holding, and that span more than one grant. Deleting a user is the clearest case: their tokens may be spread across several applications and devices, and nobody presents them to be revoked.

For these, <ProductName /> revokes by **subject**: every token issued to that user, agent, or application is rejected, across every application and device, without anyone having to present or enumerate them. Tokens already carry `sub`, so no additional claim is needed.

### User Deletion

Deleting a user revokes every token issued to them by subject and terminates their sessions, and then removes the record. This happens whichever way the user is deleted: from the Console, through the `DELETE /users/{id}` API, through SCIM with `DELETE /scim/v2/Users/{id}`, through the import API, or when a configuration version that no longer has the user is applied to a gateway.

The revocation runs as a **system flow**, built into the <ProductName /> binary, that the user service runs before it removes the record. It is not a resource: it is never stored, it cannot be edited or started through any API, and it never asks for input. If the revocation fails, the user is not deleted and the request returns an error, so the deletion can be retried. If the revocation succeeds but the removal then fails, the user stays, and their tokens and sessions stay revoked, including tokens issued to them afterwards, so retry the deletion. The revocation has no cutoff, so no system flow runs after the record is removed.

### Account Suspension

The suspend flow revokes tokens for the target subject and ends its sessions before placing the suspension. For an application or an agent with an OAuth client, it also revokes tokens issued through that client ID, including user tokens.

The revocation cutoff is the time **Validate and Plan Suspension** runs, plus `jwt.leeway`. Matching tokens issued at or before that cutoff are rejected. Unsuspending does not remove these revocation records. See [Suspend an Account](../../../account-protection/suspend-and-restore-accounts#suspend-an-account) for the administration steps.

An automatic account lock revokes nothing: it refuses new sign-ins only.

## Application Deletion and Secret Regeneration

Deleting an application revokes every token issued to it and detaches it from the sessions it took part in, and then removes the record. This happens whichever way the application is deleted: from the Console, through the `DELETE /applications/{id}` API, through Dynamic Client Registration, through the import API, or when a configuration version that no longer has the application is applied to a gateway.

Updating an application with a different client secret, through the API or the import API, revokes the tokens issued before the change in the same way, so a secret that leaked takes what it issued with it. An update that carries the secret the application already has changes nothing and revokes nothing, so an apply of a configuration version that carries the application's current secret revokes nothing. An apply that carries a different secret is a rotation, and revokes as one.

The revocation runs before the change is written, and if it fails nothing is written. Once the change is written, the revocation's cutoff moves to that moment, so a token issued while the change was being written is revoked too:

| Change | Revokes tokens issued up to | Effect after the change |
|---|---|---|
| Application deleted | The deletion | An application registered later under the same client ID (for example, by rolling back to a configuration version that still has it) is a new application. The tokens it issues are valid. |
| Client secret replaced | The new secret being written | Every token the new secret issues is valid. |

The Console's secret regeneration flow revokes until the new secret is written, as the API does.

The revocation runs as two **system flows**: flows built into the <ProductName /> binary, one that a service runs before it writes the change and one it runs after. They are not resources: they are never stored, they cannot be edited or started through any API, and they never ask for input. A failure before the write leaves the application as it was. A failure after it is reported as an error: a deletion keeps the application's record, so deleting it again revokes and removes it, and a secret replacement keeps the new secret, which the refresh grant already enforces by refusing the refresh tokens issued before it.

## Role Deletion

Deleting a role revokes the scopes it grants from the tokens its holders carry: every user, application, agent, and group member the role is assigned to, directly or through a nested group. A token that carries one of those scopes on the role's resource server is rejected. A token carrying only scopes the holder has through another role, or the same scope on another resource server, stays valid. This happens whichever way the role is deleted: from the Console or through the `DELETE /roles/{id}` API.

The revocation runs before the role is removed, and if it fails, for example because a holder sits in a group nested too deep to reach, the role is not deleted. Once the role is removed, the revocation's cutoff moves to that moment, so a token issued while the role was being removed is revoked too. A token issued after that does not carry the role's scopes, because the role no longer exists.

Like application deletion, the revocation runs as two system flows, one before the role is removed and one after. A failure after the removal is reported as an error even though the role is already gone, and a token issued during the removal stays valid until it expires. Deleting a role that no longer exists revokes nothing.

The deletion is refused, and the role kept, when the revocation is too large to plan or record:

| Error | Refused when | What to do |
|---|---|---|
| `RVS-1001` | The revocation needs more entries than `oauth.revocation.criteria.max_entries_per_change` allows (`10000` by default). It records about one entry for each holder and each scope the role grants. | Remove some of the role's assignments first, each of which revokes only that assignee's tokens, then delete the role. Or raise the limit. |
| `GRP-1017` | A holder reaches the role through a group nested too deep to walk. | Flatten the group hierarchy so that every member is within the supported depth. |
| `ROL-1017` | The server reads roles from both files and the database, and the role has more assignments than it can read in that mode. | Remove some of the role's assignments first, then delete the role. |

## Group Deletion

Deleting a group revokes the scopes its members hold through it: the permissions of the roles assigned to the group, or to a group that contains it. Members of nested groups are covered too. Each member's tokens that carry those scopes are rejected, and then the group, its role assignments, and its memberships in other groups are removed. This happens whichever way the group is deleted: from the Console, through the `DELETE /groups/{id}` API, through the import API, or when a configuration version without the group is applied to a gateway.

The revocation runs as two system flows. The first, which only a group deletion runs, runs before anything is removed and revokes the tokens issued up to that point. The group's role assignments and its memberships in other groups are then removed, which takes away what granted those scopes. The second is the same flow an [application deletion](#application-deletion-and-secret-regeneration) runs; it moves the cutoff to that moment, so a token issued while the assignments were being removed is revoked too, and only then is the group deleted. If any step fails, the group is left in place and the request returns an error; tokens already revoked stay revoked, and deleting the group again completes the removal. If the second flow is the step that failed, the role assignments are already gone, so the retry has nothing left to revoke: a token issued while the first attempt was removing them stays valid until it expires. A member that still holds a scope some other way gets it again in a new token.

The deletion is refused, and the group kept, when the revocation cannot be planned:

| Error | Refused when | What to do |
|---|---|---|
| `GRP-1017` | The group's members are nested too deep to walk. | Flatten the group hierarchy so that every member is within the supported depth. |
| `RVS-1001` | The revocation needs more entries than `oauth.revocation.criteria.max_entries_per_change` allows (`10000` by default). It records about one entry for each member and each scope the group's roles grant, so 1000 members with a role of 11 scopes are refused. | Remove some of the group's members or role assignments first, then delete the group. Or raise the limit. |

## Role Assignment Removal

Removing a role from a user, group, agent, or application revokes the tokens that assignee carries with the role's permissions, and then removes the assignment. For a group, it revokes those tokens for every member of the group. This happens whichever way the assignment is removed: from the Console, or through the `POST /roles/{id}/assignments/remove` API. A token that carries none of the role's permission scopes is not affected.

The revocation covers every scope the role grants, so a token carrying one of them is revoked even when the assignee also holds that scope through another role. A new token gets that scope again, because the other role still grants it.

Removing an assignment the role does not have changes nothing and revokes nothing. Removing a direct assignment that a sharing policy also mandates revokes nothing either, because the assignee keeps the role through the mandate.

The revocation runs as two system flows. The first, which only an assignment removal runs, runs before each assignment is removed and revokes the tokens issued up to that point. The second is the same flow an [application deletion](#application-deletion-and-secret-regeneration) runs; once the removal is written it moves the cutoff past it, so a token issued while the removal ran is revoked too. If a first flow fails, no assignment is removed. When a request names several assignees, the tokens that the earlier assignees' first flows already revoked stay revoked even though no assignment is removed. If a second flow fails, the request returns an error even though the assignments are already removed. A token issued after the removal is valid, so assigning the role again restores the assignee's access for the tokens it requests from then on.

The removal is refused, and every assignment kept, when the request names too many assignments or the revocation of a group assignment cannot be planned:

| Error | Refused when | What to do |
|---|---|---|
| `ROL-1042` | The request names more than 100 assignments. | Split the removal into requests of at most 100 assignments each. |
| `GRP-1017` | The group's members are nested too deep to walk. | Flatten the group hierarchy so that every member is within the supported depth. |
| `RVS-1001` | The revocation needs more entries than `oauth.revocation.criteria.max_entries_per_change` allows (`10000` by default). It records about one entry for each member of the group and each scope the role grants. | Remove some of the group's members first, then remove the assignment. Or raise the limit. |

## Where Revocation Is Enforced

Revocation is checked at two independent points, and they do not become consistent at the same speed.

| Enforcement point | What it covers | Freshness |
|---|---|---|
| **Authorization server** | Introspection, the refresh grant, token exchange, and internal validation | **Immediate.** Reads the denylist directly |
| **Resource server** | Requests to <ProductName />'s own protected APIs | **Eventually consistent.** Serves an in-memory snapshot refreshed on an interval |

:::note
A revoked token normally stops being accepted by a resource server within `server.security.token_revocation.sync_interval_seconds` (60 seconds by default). For an immediate answer, call [Token Introspection](../token-introspection), which reads current state. Lower the sync interval to shorten the delay, at the cost of more frequent database reads.
:::

Authorization-server enforcement **fails closed**. If the denylist cannot be read, token validation fails rather than assuming the token is good. Resource-server enforcement keeps serving its last good snapshot across a transient refresh failure.

Resource-server enforcement covers services that share this deployment's database. An external resource server with no access to it should use [Token Introspection](../token-introspection) instead.

## Configuration

Revocation behavior on the authorization server, part of [OAuth Configuration](../../../../deployment/configuration#oauth-configuration):

| Setting | Default | Description |
|---|---|---|
| `oauth.token_revocation.enabled` | `true` | Enables revocation on the authorization server: the `/oauth2/revoke` endpoint, the implicit triggers below, and the check that rejects revoked tokens during introspection, the refresh grant, and token exchange. Setting it to `false` turns off all of them, not just the endpoint |
| `oauth.revocation.token_family.on_explicit_revoke` | `true` | Revoking a token also revokes its token family |
| `oauth.revocation.token_family.on_refresh_replay` | `true` | A replayed refresh token revokes its token family. Requires `oauth.refresh_token.renew_on_grant` |
| `oauth.revocation.token_family.on_code_replay` | `true` | A replayed authorization code revokes the token family issued from it |
| `oauth.token_exchange.token_family` | `none` | `none` issues an independent token; `inherit` keeps the subject token's family |
| `oauth.refresh_token.renew_on_grant` | `false` | Issues a new refresh token on each grant. Required for rotation and replay detection |
| `oauth.refresh_token.revoke_previous_on_renew` | `true` | Revokes the consumed refresh token after rotation, making refresh tokens single-use |

Revocation enforcement on resource-server requests, part of [Security Configuration](../../../../deployment/configuration#security-configuration):

| Setting | Default | Description |
|---|---|---|
| `server.security.token_revocation.enabled` | `true` | Enforces revocation on requests to protected APIs |
| `server.security.token_revocation.source` | `db` | Where the revocation snapshot is read from. `db` is the only supported value |
| `server.security.token_revocation.sync_interval_seconds` | `60` | How often the snapshot refreshes, which sets the normal propagation delay before a revoked token stops being accepted |
